# ETF 定投与动态补仓提醒系统 PRD

> 版本：V1.5（基金级自定义回撤策略版）  
> 日期：2026-07-20  
> 状态：需求初稿
> 当前实现变更：通知渠道移除微信方式，仅保留桌面通知与 SMTP 邮件。

## 1. 产品概述

### 1.1 产品名称

ETF 定投与动态补仓提醒助手

### 1.2 产品目标

帮助用户管理场外 ETF 联接基金的定投计划，并通过其对应场内 ETF 的实时行情，自动计算是否触发额外投入档位及对应计划金额。

系统只提供计划管理、行情监控和提醒，不自动购买或赎回基金。

### 1.3 核心口径

补仓不能只看当日涨跌幅，应以场内 ETF 相对“最近 20 个交易日最高收盘价的累计回撤”触发。

每个 A 股交易日 14:50 进行一次检查，使用接口返回的最新成交价估算当前回撤。V1 当天不再进行收盘校准，提醒中必须注明实际行情时间以及“盘中估算、并非最终收盘价”。

### 1.4 核心价值

用户可以：

- 自定义场内 ETF 与场外联接基金的对应关系；
- 自定义每只基金的定投金额和定投日；
- 单独开启或关闭定投、补仓提醒；
- 每个交易日 14:50 自动检查场内 ETF；
- 可分别开启 macOS 桌面通知和邮件；
- 根据回撤档位和基础定投金额，动态计算补仓金额；
- 避免同一档位重复提醒、同一周过度补仓；
- 查看触发原因和完整计算过程。

## 2. 用户与使用场景

### 2.1 目标用户

购买场外 ETF 联接基金、采用固定定投加回撤补仓策略的个人投资者。

### 2.2 典型场景

用户添加以下配置：

| 场外联接基金 | 场外代码 | 场内 ETF | 场内代码 | 每次定投 |
|---|---:|---|---:|---:|
| 易方达中证 A500ETF 联接 A | 022459 | A500ETF 易方达 | 159361 | 600 元 |
| 国泰半导体材料设备 ETF 联接 A | 019632 | 半导体设备 ETF 国泰 | 159516 | 250 元 |
| 易方达创新药 ETF 联接 A | 019666 | 创新药 ETF 易方达 | 516080 | 200 元 |
| 招商畜牧养殖 ETF 联接 C | 014415 | 畜牧养殖 ETF 招商 | 516670 | 300 元 |

系统每个交易日 14:50 检查行情。如果 159516 相对最近 20 个交易日最高收盘价回撤达到 10%，而该基金每次定投为 250 元，则提示：

> 半导体设备 ETF 当前预计回撤 10.3%，首次进入 10% 补仓档位。  
> 基础定投金额 250 元，本档倍数 2 倍，本次额外投入计划金额 500 元。

## 4. 核心数据模型

每个基金计划保存以下信息。

### 4.1 基础信息

| 字段 | 必填 | 说明 |
|---|---|---|
| 计划名称 | 是 | 例如“A500 长期定投” |
| 场内 ETF 代码 | 是 | 用于查询行情，如 159361 |
| 场内 ETF 名称 | 否 | 可根据代码自动识别，也可手动填写 |
| 场外联接基金代码 | 是 | 实际购买对象，如 022459 |
| 场外基金名称 | 否 | 展示使用 |
| 策略类型 | 是 | V1 仅开放“长期定投回撤策略”；周期交易策略显示“暂未开放” |
| 备注 | 否 | 用户自定义说明 |

允许用户只填写代码，但系统应校验：

- 必须为合法格式；
- 场内 ETF 代码不能重复绑定到相同计划；
- 场外代码与场内代码不能填反；
- 如果无法验证两者的联接关系，提示用户人工确认，但允许继续保存。

### 4.2 定投配置

| 字段 | 默认值 | 说明 |
|---|---:|---|
| 定投开关 | 开启 | 控制定投提醒 |
| 每次定投金额 | 用户填写 | 补仓计算基数 |
| 定投频率 | 每周 | V1 主要支持每周 |
| 定投星期 | 周四 | 用户可修改 |
| 定投提醒时间 | 14:50 | 用户可修改；自动检查每天最多一次 |
| 节假日处理 | 顺延至下一交易日 | 可配置为跳过 |
| 补仓开关 | 开启 | 可独立于定投开关 |

定投开关与补仓开关应相互独立。

例如：

- 关闭定投、开启补仓：不提醒固定定投，但仍监控回撤；
- 开启定投、关闭补仓：只提醒固定定投；
- 全部关闭：保留配置但不产生提醒。

### 4.3 补仓配置

每只基金计划拥有独立的回撤策略，不使用不可修改的全局固定档位。新建计划时默认复制以下原始策略：

| 回撤档位 | 默认补仓倍数 | 默认执行方式 |
|---:|---:|---|
| 5% | 1 倍 | 单次提醒 |
| 8% | 1 倍 | 单次提醒 |
| 10% | 2 倍 | 单次提醒 |
| 15% | 1 倍 | 两期提醒，每期 1 倍，按通知送达状态推进 |
| 20% | 1 倍 | 每周最多提醒一次 |

补仓金额公式：

```text
额外投入计划金额 = 当前基金每次定投金额 × 当前档位倍数
```

例如：

```text
每次定投金额：600 元
10% 档补仓倍数：2 倍
额外投入计划金额：600 × 2 = 1200 元
```

用户修改定投金额后，后续补仓金额自动调整，不修改历史记录。

建议允许用户自定义：

- 每只基金各自的回撤档位；
- 每个档位的补仓倍数；
- 每个档位的执行方式：单次、分期或深度回撤期间按周提醒；
- 分期次数及每期间隔周数；
- 单次最大补仓金额；
- 每周最大补仓次数；
- 每周最大补仓金额；
- 是否允许补仓金额超过可用资金池（P1）。

### 4.4 基金级策略编辑器

用户可以在每只基金的计划详情中单独维护回撤阶梯。高波动基金可以使用与宽基不同的档位，例如恒生科技可以设置更深的触发区间，但系统不预设或推荐具体数值。

每一行策略至少包含：

| 字段 | 说明 |
|---|---|
| 回撤阈值 | 大于 0 的百分比，例如 12% |
| 补仓倍数 | 相对于该基金基础定投金额的倍数，例如 1.5 倍 |
| 执行方式 | 单次、分期、深度回撤期间按周 |
| 分期次数 | 执行方式为分期时必填 |
| 间隔周数 | 相邻两期之间的自然周数 |
| 是否启用 | 可临时停用该档位而不删除 |
| 单档金额上限 | 可选；限制本档计算金额 |
| 备注 | 用户记录该档位的用途 |

支持操作：

- 新增档位；
- 删除未被历史事件引用的档位；
- 停用已被历史事件引用的档位；
- 修改阈值、倍数和执行方式；
- 拖动排序，保存时仍按阈值从小到大规范化；
- 恢复原始默认策略；
- 从另一只基金复制策略；
- 将当前策略另存为个人模板；
- 从个人模板创建新计划。

配置校验：

- 同一计划的启用档位阈值不得重复；
- 阈值必须大于 0 且小于 100%；
- 补仓倍数必须大于 0，支持小数，V1 默认最多 2 位小数；
- 分期次数必须为 2—12 的整数；
- 间隔周数必须为 1—52 的整数；
- 档位金额不得超过计划设置的单次上限；
- 至少保留一个启用档位；
- 保存前展示按照当前基础金额计算的各档实际金额预览。

示例预览：

```text
基础定投金额：300 元
自定义档位：12%
补仓倍数：1.5 倍
本档计划金额：300 × 1.5 = 450 元
```

### 4.5 策略版本与生效规则

每次保存基金级策略时创建不可变的 `strategy_version`，不得直接覆盖旧版本。

用户修改策略时必须选择：

1. **下一回撤周期生效（默认、推荐）**：当前回撤周期继续使用原策略，新周期使用新版本；
2. **立即生效**：当前周期从下一次检查起使用新版本，但不得补发新策略中已经跨过的浅档位。

立即生效规则：

- 已经成功送达的旧档位不重复提醒；
- 新版本当前最高命中档位如果比所有已送达档位更深，可在下一次检查中触发；
- 删除或停用正在执行的分期档位时，必须提示是否取消未发送的后续期；
- 历史事件永久关联其触发时的策略版本和档位快照；
- 策略修改不得改变历史金额、历史倍数和历史触发原因。

### 4.6 策略模板

内置模板：

- `原始默认策略`：5%×1、8%×1、10%×2、15%两期各×1、20%深度回撤期间每周×1；
- `空白自定义策略`：用户从零添加档位。

个人模板保存：

- 模板名称；
- 回撤档位和倍数；
- 执行方式及分期配置；
- 金额上限规则；
- 创建时间和更新时间；
- 模板 UUID 和版本。

模板只保存策略规则，不保存基金代码、基础定投金额、历史事件或通知状态。

### 4.7 观察标的与购买标的

系统必须把两个对象分开保存：

```text
观察标的（Signal Asset）
- 场内 ETF；
- 用于实时行情、K 线、20 日高点及回撤计算。

购买标的（Purchase Asset）
- 场外 ETF 联接基金；
- 用于生成定投和额外投入提醒。
```

场内 ETF 行情仅是触发信号，场外联接基金最终确认净值以基金公司为准。提醒文案统一使用“按预设规则计算，本次额外投入金额为……”而非确定性的投资建议措辞。

## 5. 回撤计算规则

### 5.1 基准口径

默认采用最近 20 个已完成交易日的最高收盘价作为回撤基准。

14:50 计算时：

- 使用当前交易日前最近 20 个已完成交易日的正式收盘价；
- 不包含当前交易日；
- 使用行情源提供的前复权收盘价，避免 ETF 分红除息被误判为回撤；
- 停牌日和行情缺失日不计入 20 个有效交易日。

每天只执行一次自动检查，不做当日收盘校准。次一交易日检查时，历史窗口自然纳入前一交易日的正式收盘价。

```text
20 日最高收盘价 = 最近 20 个交易日中最高的正式收盘价

回撤幅度 =
（20 日最高收盘价 - 当前价格）÷ 20 日最高收盘价 × 100%
```

例如：

```text
20 日最高收盘价：1.000 元
14:50 最新成交价：0.898 元
当前预计回撤：10.20%
```

计算精度规则：

- 内部计算至少保留 6 位小数；
- 档位比较使用未四舍五入的原始结果；
- 页面展示保留 2 位小数；
- 触发条件统一为 `drawdown >= threshold`；
- 例如原始回撤 4.996% 即使展示为 5.00%，也不触发 5% 档。

### 5.2 为什么不只使用当日涨跌幅

当日下跌 3% 不代表已经达到 5% 累计回撤；当日上涨 1%，也可能仍处于 15% 的深度回撤区间。

因此系统同时展示：

- 当日涨跌幅；
- 当前实时价格；
- 最近 20 日最高收盘价；
- 当前累计回撤；
- 当前所处补仓档位。

补仓触发以累计回撤为准。

### 5.3 14:50 单次检查口径

14:50 获取的是盘中最新成交数据，不是最终收盘价。程序不强求行情时间精确到 `14:50:00`，而是记录接口实际返回时间。

任务流程：

```text
14:50:00 启动本地任务
14:50:00—14:50:30 获取最新行情
使用接口返回的最新成交价计算回撤
记录行情时间和任务执行时间
当天不再自动复查
```

提醒必须展示：

```text
行情价格：0.898 元
行情时间：2026-07-20 14:50:06
任务执行时间：2026-07-20 14:50:08
本次结果为盘中估算，不代表最终收盘价格。
```

14:50 触发的档位直接作为当天有效触发，不等待收盘确认。如果尾盘价格变化导致最终收盘未达到档位，系统不回滚当天事件；历史记录明确标注数据来源为“14:50 盘中最新价”。

## 6. 补仓触发机制

### 6.1 逐档触发

档位按照 5%、8%、10%、15%、20% 依次触发。

同一回撤周期内，同一档位只产生一次“首次触发事件”。是否再次提醒由事件处理状态和重复提醒规则决定。

示例：

1. 周一回撤 4%，不触发；
2. 周二回撤 5.2%，触发 5% 档；
3. 周三回撤 6%，不重复触发 5% 档；
4. 周四回撤 8.3%，触发 8% 档；
5. 周五仍为 8.5%，不重复触发。

### 6.2 快速跨档

如果 ETF 从回撤 4% 直接跌至 10%，系统不应提示用户当天连续执行 5%、8%、10% 三笔补仓。

默认规则：

- 只触发当前最高档位；
- 同一基金同一天只生成一条补仓建议；
- 建议金额受单次上限约束；
- 快速跨过的低档位不再单独补发提醒。

例如基础金额 250 元，直接进入 10% 档：

```text
当前档位：10%
建议金额：250 × 2 = 500 元
```

而不是：

```text
250 + 250 + 500 = 1000 元
```

### 6.3 每周频率限制

默认纪律：

- 同一基金一周最多补仓一次；
- 用户可将上限设置为 0、1 或更多次；
- 达到限制后，即使进入新档位，也只提示行情变化，不再建议本周加仓；
- 新一周重新获得补仓资格，但已触发档位不会自动重复触发。

如果本周已经成功发送 5% 档提醒，随后进入 8% 档：

- 创建 8% 档事件并记录为 `SUPPRESSED`；
- 告知用户已进入新档位，但受每周次数限制，本周不建议再次投入；
- 下一周仍处于 8% 或更深档位时，可重新生成一次计划提醒；
- 若下周已经进入更深档位，只处理当前最高档位。

### 6.4 15% 两期补仓计划

首次正式确认进入 15% 档时创建两期计划：

```text
第一期：触发所在周，按 1 倍基础金额提醒。
第二期：下一自然周仍满足回撤 >= 15%，且第一期至少一个通知渠道已成功送达时，再按 1 倍提醒。
```

规则如下：

- 第一周至少一个渠道发送成功后，即视为第一期已经完成提醒；是否实际投入不影响第二期判断；
- 第一周所有启用渠道均发送失败时，第一期保持未送达并按失败策略重试，不生成第二期；
- 第二周回撤恢复至 15% 以下，取消第二期；
- 从 14% 直接进入 20% 时，只处理 20% 当前最高档，不同时创建 15% 计划；
- 15% 两期计划存续期间进入 20% 档，尚未发送的 15% 后续期取消，改按 20% 档处理；
- 每周次数和单次金额上限仍然有效。

### 6.5 回撤周期重置

默认建议：

> 场内 ETF 在连续 2 次交易日 14:50 检查中，最新价均达到对应 20 日最高收盘价的 98% 以上，视为本轮回撤结束。

重置后：

- 5%、8%、10% 等档位恢复为“未触发”；
- 下一轮新的回撤可以再次触发；
- 历史补仓记录保留。

该条件建议做成可配置项。

### 6.6 补仓事件与执行状态

每次触发生成独立补仓事件。系统判断依据是“事件是否生成、通知是否成功送达”，而不是用户是否实际投入。

事件状态定义如下：

| 状态 | 含义 | 是否占用正式档位资格 |
|---|---|---|
| `CREATED` | 14:50 已触发，等待发送通知 | 是 |
| `NOTIFIED` | 至少一个启用渠道发送成功 | 是 |
| `DELIVERY_FAILED` | 所有启用渠道均发送失败 | 否，等待重试 |
| `IGNORED` | 用户主动忽略本档 | 是 |
| `POSTPONED` | 延迟到下一交易日提醒 | 是 |
| `SUPPRESSED` | 因周次数限制未建议执行 | 否 |
| `EXPIRED` | 超过事件有效期 | 是 |

状态转换规则：

- `CREATED → NOTIFIED`：任一启用渠道发送成功；占用本周提醒次数和本轮档位资格；
- `CREATED → DELIVERY_FAILED`：所有渠道发送失败；不占用本周提醒次数，按通知重试策略处理；
- `NOTIFIED → IGNORED`：本回撤周期不再提醒同档，进入更深档仍可提醒；
- `NOTIFIED → POSTPONED`：下一交易日 14:50 检查后提醒一次；如果届时已经脱离该档位，则转为 `EXPIRED`；
- 当天不根据最终收盘价回滚或修改事件。

实际投入状态作为独立、可选字段保存：

```text
execution_status：UNKNOWN / EXECUTED / NOT_EXECUTED
executed_amount：用户可选填写的实际金额
executed_at：用户可选填写的执行时间
```

默认值为 `UNKNOWN`。用户只看邮件而不返回确认时，事件仍可正常推进，下一次计算不得因 `execution_status=UNKNOWN` 卡住，也不得假设用户已经买入。

## 7. 定投提醒规则

### 7.1 正常定投

定投开启且当天为设置的定投日时，14:50 生成提醒：

> 今天是 A500 联接基金定投日，计划定投 600 元。  
> 场外代码：022459；观察 ETF：159361。

### 7.2 定投日同时触发补仓

定投金额和补仓金额分开展示：

```text
正常定投：600 元
额外补仓：600 元
今日计划合计：1200 元
```

不能把固定定投误记为补仓。

### 7.3 定投关闭时

如果定投关闭，但补仓开启：

- 不产生固定定投提醒；
- 补仓金额仍以配置的“基础金额”计算；
- 页面明确说明该金额仅作为补仓计算基数。

这意味着即使关闭定投，仍须保留“每次基础金额”。

### 7.4 金额修改

用户把每次定投从 600 元调整为 800 元后：

- 下一次固定定投为 800 元；
- 5% 档补仓变为 800 元；
- 10% 档补仓变为 1600 元；
- 修改之前的提醒和历史记录仍保留原金额。

### 7.5 节假日顺延与周期去重

每次固定定投任务必须绑定定投周期编号，例如 `2026-W30`。

- 周四休市时，默认顺延至下一交易日；
- 连续休市时持续顺延，但同一周期只生成一笔提醒；
- 若顺延日与下一周期正常定投日为同一天，分别展示两期金额，并要求用户确认是否合并执行；
- 用户选择“跳过”时，本周期不再补发；
- 用户修改定投星期后，尚未生成的旧计划任务取消，已经生成的提醒保留历史；
- 场外基金暂停申购时，任务标记为不可执行并停止提醒，恢复申购后不自动补发过期任务。

## 8. 资金池控制（P1）

为了避免多个基金同时触发后，建议金额超出每月预算，P1 增加“补仓资金池”。V1 仅展示各计划理论金额及合计，不自动占用、扣减或分配额度。

### 8.1 配置字段

- 每月投资预算；
- 每月固定定投预计金额；
- 本月补仓池金额；
- 本月已补仓金额；
- 当前剩余额度；
- 是否允许额度结转至下月。

### 8.2 资金不足时

当建议补仓金额超过资金池余额时，显示：

```text
理论建议补仓：1200 元
补仓池剩余：800 元
受资金池限制，本次建议最多补仓：800 元
```

P1 允许用户给计划设置优先级：

1. 核心宽基；
2. 行业增强；
3. 周期交易。

多个基金同时触发时，排序规则为：

1. 用户手动优先级；
2. 回撤档位由高到低；
3. 首次触发时间由早到晚；
4. 计划创建时间由早到晚。

V1 不自动分配额度，仅提醒理论合计可能超过预算；P1 再支持按顺序全额满足或按比例分配。

### 9.1 提醒渠道配置

## 11. 用户操作状态

提醒生成后，用户可以选择：

- 已补仓；
- 暂不补仓；
- 忽略本次；
- 延迟到下一个交易日提醒；
- 修改本次金额；
- 查看计算过程。

本周次数限制以“至少一个渠道成功送达提醒”为准，而不是以用户确认实际投入为准。用户点击“已补仓”时，系统只记录可选的实际执行信息，不改变此前已经占用的提醒次数。V1 不维护全局资金池余额。

如果用户没有反馈：

- 系统不能默认其已经执行；
- 当天不重复提醒；
- 事件执行状态保持 `UNKNOWN`；
- 不影响下一交易日、新档位或15%第二期提醒的正常计算。

用户操作的具体状态转换以 6.6 节补仓事件状态机为准。

## 12. 非交易日及异常处理

### 12.1 非交易日

周末、法定节假日或休市日：

- 不获取盘中行情；
- 不触发补仓；
- 定投提醒按用户设置选择“顺延”或“跳过”。

所有交易判断固定使用 `Asia/Shanghai` 时区和中国大陆交易所交易日历，不使用用户电脑本地时区。交易日历支持临时休市人工配置。

### 12.2 行情获取失败

数据源超时或数据异常时：

- 不使用旧价格生成新的补仓建议；
- 展示最后成功更新时间；
- 标记“行情数据不可用”；
- 自动重试最多 3 次；
- 支持用户手动刷新。

### 12.3 极端数据保护

出现以下情况时停止计算：

- ETF 代码不存在；
- 当前价格为 0；
- 最近 20 日数据不足；
- 价格出现明显异常跳变；
- ETF 停牌；
- 数据时间不是当天；
- 行情源返回非交易状态。

新上市 ETF 不足 20 个交易日时，可使用现有全部交易日，但须明确标注“历史数据不足 20 日”。

## 13. 定时任务幂等与并发

14:50 定时任务、人工刷新和失败重试可能同时运行，系统必须保证不会生成重复事件。

事件幂等键：

```text
plan_id + trading_date + drawdown_cycle_id + level_id
```

规则：

- 相同幂等键只能成功创建一条事件；
- 重复任务只更新行情检查日志，不重复发送通知；
- 多基金可以并行计算，每个计划内部必须串行更新档位状态；
- 手动刷新不能绕过每周次数、档位状态、每日单次触发和幂等规则；
- 所有定时任务记录开始时间、结束时间、执行结果和错误信息。

## 14. 默认策略配置

系统首次创建长期定投计划时，默认使用：

```text
回撤窗口：20 个交易日
5% 档：1 倍
8% 档：1 倍
10% 档：2 倍
15% 档：首次确认后创建两期计划，每期 1 倍
20% 以上：每周 1 倍
同一基金每周最多补仓：1 次
单日最多触发：1 次
档位重置：恢复至 20 日最高收盘价 98% 以上并维持 2 日
```

周期类基金独立模板规划如下，但 V1 不开放：

```text
首次观察仓：1 倍基础金额
相对用户参考成本下跌 5%：再补 1 倍
重新站上 5 日均线并维持 2 日：再补 1 倍
仓位上限：由用户自行填写
不进行无限期自动定投
```

周期策略依赖用户真实成本和趋势条件，放到后续版本；V1 只支持长期定投回撤策略。

## 15. 验收标准

### 15.1 基金配置

- 能添加场内 ETF 代码和场外联接基金代码；
- 能设置每次定投金额；
- 能设置星期一至星期五中的任意定投日；
- 能独立关闭定投和补仓；
- 修改金额后，下一次计算立即使用新金额。

### 15.2 行情计算

- 每个交易日 14:50 自动获取一次行情；
- 能取得当日涨跌幅、实时价格和最近 20 日收盘价；
- 正确计算 20 日最高收盘价及回撤；
- 非交易日不生成错误提醒；
- 数据失败时不生成基于旧行情的新建议。

### 15.3 补仓计算

假设基础定投金额为 600 元：

- 回撤 4.99%：不补仓；
- 首次达到 5%：建议 600 元；
- 首次达到 8%：建议 600 元；
- 首次达到 10%：建议 1200 元；
- 相同档位第二次检查：不重复建议；
- 基础金额改为 800 元后，10% 档建议 1600 元；
- 本周已补仓时，本周再次触发不得重复建议。

### 15.4 提醒

- 定投日显示固定定投金额；
- 达到补仓档位显示额外补仓金额；
- 同时发生时分项显示并计算合计；
- 每条提醒展示完整计算依据；
- 明确标注 14:50 数据属于盘中估算并展示实际行情时间。

### 15.5 边界、状态与幂等测试

1. 原始回撤恰好等于 5.000000% 时触发；
2. 展示为 5.00%、原始值为 4.996% 时不触发；
3. 一天从 4% 直接跨到 10%，只生成一条 10% 提醒；
4. 14:50 达到 10% 时生成当天有效事件，之后不因收盘价格变化回滚；
5. 14:50 未达到 10% 时当天不再自动补发，下一交易日重新检查；
6. 本周已成功发送 5% 档提醒后进入 8% 档，事件标记为 `SUPPRESSED`；
7. 8% 档本周因次数限制被 `SUPPRESSED`，下周仍处于该档时允许重新提醒；
8. 用户忽略 8% 档后，同轮进入 10% 档仍可提醒；
9. 定时任务重复执行两次，不得生成两条相同提醒；
10. 行情时间戳不是当天或超过允许时效，不得触发；
11. 修改基础金额后，旧事件金额和配置快照不得变化；
12. 修改档位配置仅影响修改后新生成的事件；
13. 删除或归档计划后，历史记录仍可查看；
14. 新上市 ETF 只有 8 个有效交易日时正确计算并显示提示；
15. 多基金同时触发时，理论合计金额正确；
16. 节假日顺延后，同一定投周期不得重复生成任务；
17. 用户确认已执行后，保留当时行情、金额、档位及渠道发送快照；
18. 15% 第一期所有渠道均发送失败时，不得生成第二期；至少一个渠道送达且下周仍满足15%时可以生成；
19. 15% 计划存续期间进入 20% 档时，尚未发送的 15% 后续期被取消；
20. ETF 除息时使用复权数据，不得因机械价格缺口误触发。

## 16. 非功能需求

### 16.1 数据及时性

- 14:50 任务允许延迟不超过 5 分钟；
- 行情时间戳与当前时间相差超过 10 分钟时视为过期数据；
- 单次检查应在 2 分钟内完成，单只 ETF 失败不得阻塞其他计划。

### 16.2 可用性与容错

- 行情获取失败自动重试 3 次；
- 重试间隔采用递增策略；
- 仍失败时记录异常并通知用户，不生成投入建议；
- 单个 ETF 获取失败不得阻塞其他计划计算。

### 16.3 审计记录

每次计算必须保存：

- 使用价格、价格类型及行情时间；
- 20 日历史数据起止日期；
- 回撤基准最高价；
- 原始回撤结果及展示结果；
- 档位配置快照；
- 基础定投金额快照；
- 每周次数限制快照；
- 14:50 预计档位及实际行情时间；
- 最终事件及用户操作结果。

### 16.4 安全与隐私

- V1 不采集支付宝、银行卡或券商账号密码；
- 不保存可用于真实交易的授权凭证；
- 用户计划及执行记录仅供本人查看；
- 配置修改、删除和事件状态变化必须写入审计日志。

## 18. 最终业务规则摘要

```text
1. 用户自行添加场内 ETF 和场外联接基金。
2. 用户自行设置定投金额、定投星期及相关开关。
3. 每个交易日 14:50 在 Mac 本地获取一次场内 ETF 最新行情。
4. 同时获取最近 20 个交易日正式收盘价。
5. 用当前价计算相对 20 日最高收盘价的预计回撤。
6. 回撤首次达到 5%、8%、10%、15%、20% 档位时触发。
7. 补仓金额 = 当前基础定投金额 × 对应档位倍数。
8. 修改基础定投金额后，补仓建议动态变化。
9. 同一回撤周期内，同一档位只创建一次首次触发事件，重复提醒由事件状态决定。
10. 同一基金默认每周最多成功发送一次额外投入提醒。
11. 定投关闭不等于补仓关闭，两者独立控制。
12. 系统只提醒，不自动执行基金交易。
13. 14:50 触发即作为当天有效事件，系统不做收盘校准或回滚。
14. 每条历史事件保存行情、金额和规则快照。
15. 定时任务和人工刷新必须通过幂等键防止重复提醒。
```

## 19. 成功标准

系统给出的每一笔补仓建议，都必须能够清楚回答：

- 依据的是哪个场内 ETF；
- 使用的是哪个价格；
- 当前累计回撤是多少；
- 触发了哪个补仓档位；
- 基础定投金额是多少；
- 补仓倍数是多少；
- 为什么建议补这个金额；
- 是否受到每周次数限制，以及 P1 启用后是否受到资金池额度限制。

## 20. macOS 本地部署方案

### 20.1 产品形态

V1 定位为单用户、个人自用的 macOS 本地工具，不部署公网服务，不要求域名、云服务器或微信小程序。

推荐组成：

```text
本地管理页面（Streamlit）
        ↓
SQLite 本地数据库
        ↓
macOS launchd 每个工作日 14:50 启动 daily_check.py
        ↓
行情适配器批量获取最新价和历史日线
        ↓
计算回撤、生成事件、写入历史
        ↓
macOS 桌面通知 / SMTP 邮件 / 微信消息适配器
```

代码结构建议：

```text
app.py                 本地配置和历史查看页面
daily_check.py         14:50 单次检查入口
core/                  回撤、档位和状态机纯业务逻辑
providers/market/      行情数据适配器
providers/notify/      桌面、邮件、微信通知适配器
storage/               SQLite 数据访问和迁移
tests/                 计算、状态、调度和通知测试
```

页面程序与定时任务必须分离。关闭管理页面不能影响 `daily_check.py` 被 `launchd` 调用。

### 20.2 技术选型

| 模块 | V1 方案 |
|---|---|
| 开发语言 | Python 3 |
| 本地页面 | Streamlit |
| 数据库 | SQLite |
| 行情 | 行情适配器接口；首个实现可使用 AKShare，允许后续替换 |
| 调度 | macOS `launchd` |
| 桌面通知 | macOS 通知中心 |
| 邮件 | SMTP，支持 SSL/TLS |
| 微信 | Webhook/第三方推送适配器，不模拟操作微信客户端 |
| 日志 | Python logging，按大小或日期轮转 |
| 密钥保存 | macOS Keychain；数据库只保存密钥引用或脱敏值 |

行情模块必须通过统一接口隔离：

```text
get_latest_quotes(symbols)
get_daily_history(symbol, completed_trade_days=20, adjust="qfq")
```

不得把某个免费行情网站的字段和请求逻辑散落在业务计算代码中。行情源失败时可以整体升级或替换而不改补仓规则。

### 20.3 Mac 运行前提

用户的 MacBook 运行条件：

- 保持开盖；
- 长期连接电源；
- 可以锁屏、关闭显示器；
- 系统本身不得进入睡眠；
- 当前用户保持登录；
- 14:50 前后保持网络连接；
- 已授予应用通知权限；
- 若启用邮件或微信，相关配置已经通过“发送测试消息”。

锁屏不会阻止任务运行，但睡眠、合盖睡眠、关机或断网都会影响任务。应用首页必须展示：

- 上一次成功检查时间；
- 下一次计划检查时间；
- 最近一次失败原因；
- 当前通知渠道健康状态；
- 最近一次行情成功时间。

### 20.4 launchd 调度规则

`launchd` 每周一至周五 14:50 尝试执行，但脚本启动后仍须自行判断 A 股交易日和有效执行时间。

```text
有效执行窗口：交易日 14:45:00—15:00:00
正常计划时间：14:50:00
允许启动延迟：5 分钟
最大运行时间：2 分钟
失败重试：间隔 60 秒，最多 2 次
```

如果 Mac 因睡眠等原因在 15:00 后才补启动：

- 不生成“今天应投入”的补仓提醒；
- 记录 `MISSED_EXECUTION_WINDOW`；
- 发送一条运行异常通知；
- 用户可以手动检查，但结果明确标记为盘后数据，不占用当天 14:50 档位资格。

### 20.5 单次任务执行流程

```text
1. 获取本地进程锁，防止重复运行；
2. 校验 Asia/Shanghai 时间和 A 股交易日；
3. 校验是否处于有效执行窗口；
4. 读取 SQLite 中已启用的计划；
5. 批量获取场内 ETF 最新行情；
6. 获取每只 ETF 最近 20 个已完成交易日的前复权收盘价；
7. 校验行情时间、价格和数据完整性；
8. 计算 20 日最高收盘价及当前回撤；
9. 判断档位、回撤周期、每周次数及幂等键；
10. 计算正常定投金额和额外投入金额；
11. 在同一数据库事务中保存计算快照和事件；
12. 按用户配置发送桌面、邮件和微信消息；
13. 分渠道记录发送结果；
14. 释放进程锁并写入任务完成日志。
```

### 20.6 本地数据与备份

- SQLite 数据库存放于应用数据目录，不放在程序安装目录；
- 支持手动导出计划、事件和执行历史为 CSV；
- 支持一键备份数据库；
- 导入备份前校验数据库版本和完整性；
- 删除计划采用归档方式，历史事件不物理删除；
- SMTP 密码、Webhook Token 等敏感数据不得明文导出。

### 20.7 通知渠道验收

macOS 桌面通知：

- Mac 开盖、接电、锁屏但未睡眠时，14:50 可以成功显示通知；
- 用户关闭锁屏内容预览时，不在锁屏界面泄露基金和金额；
- 点击通知可以打开本地详情页。

邮件：

- 配置保存前必须测试连接；
- 发送失败重试 2 次并记录 SMTP 错误；
- 日志和页面不得显示完整邮箱密码或授权码。

微信：

- 用户必须自行配置受支持的 Webhook 或推送服务凭证；
- 首次保存前发送测试消息；
- 接口失败不影响桌面和邮件通知；
- 不使用个人微信账号密码，不模拟扫码登录，不自动控制微信客户端；
- 切换微信推送服务时不得修改补仓计算和事件状态逻辑。

### 20.8 本地版不包含

- 多用户注册和权限系统；
- 云端数据库及多设备同步；
- 公网远程访问；
- 微信小程序；
- 自动控制支付宝、券商或基金交易；
- 电脑睡眠、关机时的云端兜底检查；
- 个人微信客户端自动化。

## 21. 计划导入导出与跨环境迁移

### 21.1 目标

用户能够从 A 环境导出全部业务数据，再导入 B 环境继续使用。迁移后计划配置、历史行情快照、提醒事件、通知记录和可选执行记录保持一致，不要求重新创建计划，也不重复触发已经送达的历史档位。

支持的迁移方向：

```text
macOS → macOS
Windows → Windows
macOS → Windows
Windows → macOS
```

操作系统相关配置不得阻碍业务数据迁移。

### 21.2 导出范围

默认“完整迁移包”包含：

- 基金计划及场内、场外代码映射；
- 定投金额、日期、开关和节假日策略；
- 回撤档位、倍数、每周限制及配置版本；
- 回撤周期和已触发档位状态；
- 历史计算快照；
- 补仓事件及通知送达状态；
- 用户可选记录的实际投入状态和金额；
- 定时任务运行历史和非敏感错误摘要；
- 应用设置、消息模板及通知渠道开关；
- 数据库结构版本和应用版本。

默认不导出：

- SMTP 密码或授权码；
- 微信 Webhook Token、Secret 等凭证；
- macOS Keychain 或 Windows Credential Manager 中的内容；
- 日志中的完整第三方响应、个人密码和访问令牌；
- 操作系统绝对路径及本机设备标识。

### 21.3 迁移包格式

导出为单个文件：

```text
etf-assistant-backup_YYYYMMDD_HHMMSS.etfbak
```

`.etfbak` 本质为 ZIP 容器，至少包含：

```text
manifest.json           迁移包元数据、版本、文件清单和校验值
data.sqlite             一致性快照数据库
settings.json           跨平台非敏感设置
templates.json          用户自定义消息模板
checksums.sha256        每个文件的 SHA-256
README.txt              恢复说明和敏感配置提醒
```

`manifest.json` 至少包含：

```json
{
  "format_version": 1,
  "app_version": "1.0.0",
  "schema_version": 1,
  "exported_at": "2026-07-20T14:50:00+08:00",
  "source_os": "macOS",
  "timezone": "Asia/Shanghai",
  "contains_secrets": false
}
```

### 21.4 导出流程

```text
1. 暂停写入并获取数据库备份锁；
2. 使用 SQLite Online Backup API 生成一致性快照；
3. 导出跨平台非敏感配置和消息模板；
4. 生成 manifest 和 SHA-256 校验值；
5. 打包到临时文件；
6. 完整校验迁移包；
7. 原子重命名为最终 .etfbak 文件；
8. 释放锁并记录导出审计事件。
```

导出失败不得留下看似成功但不完整的迁移包。

### 21.5 导入模式

提供两种模式：

1. **整库恢复（推荐）**：B 环境为空或用户希望完全替换时使用；
2. **合并导入**：B 环境已有数据时使用，通过稳定 UUID 合并计划和事件。

整库恢复规则：

- 导入前自动备份 B 环境现有数据库；
- 校验文件类型、格式版本、结构版本和所有 SHA-256；
- 在临时目录完成数据库迁移和完整性检查；
- 全部成功后原子替换正式数据库；
- 任一步失败均回滚，原环境继续可用。

合并导入规则：

- 计划、回撤周期和事件必须使用跨环境稳定 UUID，不依赖本地自增 ID；
- 相同 UUID 的历史事件不得重复插入；
- 相同计划 UUID 但配置不同，默认保留更新时间较新的版本，并在导入前展示差异；
- 用户可选择“保留本机”“采用导入版本”或“复制为新计划”；
- 通知发送记录只合并，不重新发送；
- 已送达档位和周次数状态必须延续，防止迁移后重复提醒；
- 导入期间不运行 14:50 自动任务。

### 21.6 密钥恢复

迁移完成后，对已开启但缺少凭证的渠道标记为 `NEEDS_RECONFIGURATION`：

- 桌面通知只需在新环境重新授权；
- 邮件需要重新录入 SMTP 密码或授权码；
- 微信需要重新录入 Webhook 或推送服务凭证；
- 用户必须完成“发送测试消息”，渠道才恢复为可用状态；
- 一个渠道待配置不得影响其他渠道和行情检查。

### 21.7 导入导出验收标准

1. A 环境完整导出后，B 环境整库恢复的数据总量、计划 UUID 和事件 UUID 一致；
2. macOS 导出的迁移包能在 Windows 版本导入，反向亦然；
3. 迁移后已触发档位不重复提醒；
4. 迁移后下一次 14:50 检查可基于原回撤周期继续计算；
5. 迁移包篡改任意字节后校验失败且不得导入；
6. 不兼容的未来结构版本必须拒绝导入并给出升级提示；
7. 旧结构版本在临时副本完成数据库迁移后才能替换正式库；
8. 导入中断、磁盘不足或结构迁移失败时，B 环境原数据不受损；
9. 合并导入重复执行两次，不产生重复计划或事件；
10. 迁移包中不存在明文 SMTP 密码、Webhook Token 或其他凭证；
11. 导入成功后，缺少凭证的通知渠道准确标记为待配置；
12. 导出时应用仍可查看数据，但禁止并发修改直至快照完成。

## 22. Windows与macOS双端交付

### 22.1 交付目标

同一套 Python 业务代码支持：

- Windows 10/11 x64 安装包或便携版 EXE；
- macOS DMG，分别支持 Apple Silicon 和 Intel，或提供 Universal 2 构建；
- 两端使用相同数据库结构、迁移包格式和业务规则；
- 用户不需要预装 Python 或手动安装依赖。

### 22.2 平台抽象

平台相关能力必须通过接口隔离：

```text
SchedulerProvider
├── MacOSLaunchdProvider
└── WindowsTaskSchedulerProvider

DesktopNotificationProvider
├── MacOSNotificationProvider
└── WindowsToastProvider

CredentialStore
├── MacOSKeychainStore
└── WindowsCredentialManagerStore
```

行情、回撤、档位、迁移、消息模板和 SQLite 逻辑不得包含平台判断。

### 22.3 打包策略

- 使用 PyInstaller 或经过验证的同类工具分别在对应操作系统原生构建；
- 不从 Windows 交叉生成 DMG，也不从 macOS 直接生成 Windows EXE；
- GitHub Actions 使用 Windows 和 macOS 构建矩阵；
- 每个发布物生成 SHA-256 校验文件；
- macOS 正式分发需规划代码签名和公证；未签名测试包必须明确提示 Gatekeeper 限制；
- Windows 正式分发需规划代码签名；未签名测试包必须说明 SmartScreen 提示；
- 打包后首次启动自动创建应用数据目录和数据库，不覆盖已有数据。

### 22.4 部署指南

仓库必须提供：

```text
README.md                         项目介绍和快速开始
docs/macos-installation.md        macOS 安装、权限、开盖接电与防睡眠设置
docs/windows-installation.md      Windows 安装、任务计划和通知权限
docs/notification-setup.md        桌面、SMTP 和微信渠道配置
docs/backup-and-migration.md      导出、导入、合并、回滚和密钥重配
docs/troubleshooting.md           行情、定时任务、通知和数据库排障
docs/development.md               本地开发、测试和打包命令
SECURITY.md                       凭证处理和漏洞报告方式
```

所有指南必须在干净环境中走查，不得只记录开发机器上的隐含步骤。

### 22.5 测试与发布门槛

上传 GitHub 和创建 Release 前必须完成：

- 回撤计算和档位状态机单元测试；
- 提醒送达闭环和消息模板快照测试；
- SQLite 结构迁移测试；
- 完整恢复、合并导入、重复导入和损坏包测试；
- macOS ↔ Windows 跨平台迁移测试；
- 行情失败、断网、过期行情和任务重复启动测试；
- SMTP、微信适配器的模拟测试，不在 CI 使用真实密钥；
- EXE 和 DMG 的全新安装、升级、卸载及数据保留测试；
- macOS 锁屏未睡眠条件下的 14:50 任务测试；
- Windows 锁屏条件下的任务测试；
- 文档安装步骤走查；
- 所有自动化测试通过且无高危依赖漏洞。

### 22.6 GitHub交付

最终仓库至少包含：

- 完整源代码；

任何真实邮箱密码、Webhook、访问令牌、个人基金数据和本地数据库都不得提交到 GitHub。最终推送和创建 Release 前，应由用户确认目标仓库、可见性和发布版本号。
