# ETF 定投、动态补仓与止盈恢复提醒系统 PRD

> 版本：V1.7（止盈减投与双阶段回撤版）
> 日期：2026-07-30
> 状态：V1.7 需求已确认，待实现与验收；V1.6 功能保持不变
> 当前实现变更：通知渠道移除微信方式，仅保留桌面通知与 SMTP 邮件。

## 1. 产品概述

### 1.1 产品名称

ETF 定投、动态补仓与止盈恢复提醒助手

### 1.2 产品目标

帮助用户管理场外 ETF 联接基金的定投计划，并通过其对应场内 ETF 的实时行情，自动计算是否触发额外投入、分批止盈、降低定投或恢复定投。

系统只提供计划管理、行情监控和提醒，不自动购买或赎回基金。

### 1.3 核心口径

正常定投状态下的补仓不能只看当日涨跌幅，应以场内 ETF 相对“最近 20 个交易日最高收盘价的累计回撤”触发。

首次止盈后的定投恢复不得使用 20 日最高价，而应相对“首次止盈后形成的止盈阶段最高价”判断。正常补仓高点与止盈阶段高点必须作为两套独立状态保存、计算和展示。

业务口径统一为：每个 A 股交易日 14:50 进行一次正式检查，使用接口返回的最新成交价估算当前回撤。操作系统调度器可以在每周一至周五 14:50 尝试启动任务，但脚本必须先校验 A 股交易日；非交易日不得形成正式检查。V1 当天不再进行收盘校准，提醒中必须注明实际行情时间以及“盘中估算、并非最终收盘价”。

### 1.4 核心价值

用户可以：

- 自定义场内 ETF 与场外联接基金的对应关系；
- 自定义每只基金的定投金额和定投日；
- 单独开启或关闭定投、补仓提醒；
- 每个交易日 14:50 自动检查场内 ETF；
- 可分别开启 macOS 桌面通知和邮件；
- 每个 A 股交易日 14:50 发送一封合并邮件，无操作时也发送；
- 根据回撤档位和基础定投金额，动态计算补仓金额；
- 根据用户锁定的止盈基准成本计算分批止盈位置；
- 止盈后降低定投金额，并按止盈阶段高点的回撤逐档恢复；
- 避免同一档位重复提醒、同一周过度补仓；
- 查看触发原因和完整计算过程。

## 2. 用户与使用场景

### 2.1 目标用户

购买场外 ETF 联接基金、采用固定定投加回撤补仓策略的个人投资者。

### 2.2 典型场景

用户添加以下配置：

| 场外联接基金 | 场外代码 | 场内 ETF | 场内代码 | 每次定投 |
|---|---:|---|---:|---:|
| 易方达中证 A500ETF 联接 A | 022459 | A500ETF 易方达 | 159361 | 600 元 |
| 国泰半导体材料设备 ETF 联接 A | 019632 | 半导体设备 ETF 国泰 | 159516 | 250 元 |
| 易方达创新药 ETF 联接 A | 019666 | 创新药 ETF 易方达 | 516080 | 200 元 |
| 招商畜牧养殖 ETF 联接 C | 014415 | 畜牧养殖 ETF 招商 | 516670 | 300 元 |

系统每个交易日 14:50 检查行情。如果 159516 相对最近 20 个交易日最高收盘价回撤达到 10%，而该基金每次定投为 250 元，则提示：

> 半导体设备 ETF 当前预计回撤 10.3%，首次进入 10% 补仓档位。  
> 基础定投金额 250 元，本档倍数 2 倍，本次额外投入计划金额 500 元。

## 4. 核心数据模型

每个基金计划保存以下信息。

### 4.1 基础信息

| 字段 | 必填 | 说明 |
|---|---|---|
| 计划名称 | 是 | 例如“A500 长期定投” |
| 场内 ETF 代码 | 是 | 用于查询行情，如 159361 |
| 场内 ETF 名称 | 否 | 可根据代码自动识别，也可手动填写 |
| 场外联接基金代码 | 是 | 实际购买对象，如 022459 |
| 场外基金名称 | 否 | 展示使用 |
| 策略类型 | 是 | V1 仅开放“长期定投回撤策略”；周期交易策略显示“暂未开放” |
| 计划状态 | 系统生成 | `ACTIVE / ARCHIVED`；删除操作实际转为归档 |
| 备注 | 否 | 用户自定义说明 |

允许用户只填写代码，但系统应校验：

- 必须为合法格式；
- 场内 ETF 代码不能重复绑定到相同计划；
- 场外代码与场内代码不能填反；
- 如果无法验证两者的联接关系，提示用户人工确认，但允许继续保存。

### 4.2 定投配置

| 字段 | 默认值 | 说明 |
|---|---:|---|
| 定投开关 | 开启 | 控制定投提醒 |
| 100% 正常定投金额 | 用户填写，可随时修改 | 正常状态定投金额，也是补仓计算基数 |
| 当前阶段定投金额 | 系统计算、用户可确认修改 | 止盈减投或回撤恢复后的实际定投金额 |
| 定投频率 | 每周 | V1 主要支持每周 |
| 定投星期 | 周四 | 用户可修改 |
| 定投提醒时间 | 14:50 | 用户可修改；自动检查每天最多一次 |
| 节假日处理 | 顺延至下一交易日 | 可配置为跳过 |
| 补仓开关 | 开启 | 可独立于定投开关 |

定投开关与补仓开关应相互独立。

正常定投金额不是锁定参数。用户可以在基金管理或计划详情中随时修改；程序不得因为曾经保存过策略、发生过补仓或进入过止盈周期而禁止修改。

例如：

- 关闭定投、开启补仓：不提醒固定定投，但仍监控回撤；
- 开启定投、关闭补仓：只提醒固定定投；
- 全部关闭：保留配置但不产生提醒。

### 4.3 补仓配置

每只基金计划拥有独立的回撤策略，不使用不可修改的全局固定档位。新建或编辑计划时，可以选择初始化模板；模板只复制初始参数，保存后仍是基金级独立策略，不会随模板变化自动覆盖。

| 模板 | 回撤档位 | 适用方向 |
|---|---|---|
| 稳健 / 低波 | 3%、5%、8%、12%、18% | 红利、低波 |
| 核心宽基 | 4%、7%、10%、15%、22% | A500、沪深 300 等 |
| 高波宽基 | 5%、9%、14%、20%、28% | 创业板、科创、纳指 |
| 行业主题 | 6%、11%、17%、25%、35% | 半导体、创新药、养殖等 |
| 完全自定义 | 用户填写 | 其他资产 |

每套推荐模板的前三档分别为 1 倍、1 倍、2 倍单次提醒，第四档为 1 倍两期提醒，最深档为每周 1 倍的持续补仓；持续补仓默认最多 4 周且单段累计不超过 4 倍基础金额。

补仓金额公式：

```text
额外投入计划金额 = 当前基金每次定投金额 × 当前档位倍数
```

例如：

```text
每次定投金额：600 元
10% 档补仓倍数：2 倍
额外投入计划金额：600 × 2 = 1200 元
```

用户修改定投金额后，后续补仓金额自动调整，不修改历史记录。

建议允许用户自定义：

- 每只基金各自的回撤档位；
- 每个档位的补仓倍数；
- 每个档位的执行方式：单次、分期或深度回撤期间按周提醒；
- 分期次数及每期间隔周数；
- 单次最大补仓金额；
- 每周最大补仓次数；
- 每周最大补仓金额；
- 持续补仓最大执行周数；
- 单周期累计补仓金额和倍数上限；
- 是否允许补仓金额超过可用资金池（P1）。

### 4.4 基金级策略编辑器

用户可以在每只基金的计划详情中单独维护回撤阶梯。高波动基金可以使用与宽基不同的档位；模板是可编辑的初始化建议，不代表系统判断某套参数一定最优。

每一行策略至少包含：

| 字段 | 说明 |
|---|---|
| 回撤阈值 | 大于 0 的百分比，例如 12% |
| 补仓倍数 | 相对于该基金基础定投金额的倍数，例如 1.5 倍 |
| 执行方式 | 单次、分期、深度回撤期间按周 |
| 分期次数 | 执行方式为分期时必填 |
| 间隔周数 | 相邻两期之间的自然周数 |
| 是否启用 | 可临时停用该档位而不删除 |
| 单档金额上限 | 可选；限制本档计算金额 |
| 备注 | 用户记录该档位的用途 |

支持操作：

- 新增档位；
- 删除未被历史事件引用的档位；
- 停用已被历史事件引用的档位；
- 修改阈值、倍数和执行方式；
- 拖动排序，保存时仍按阈值从小到大规范化；
- 恢复原始默认策略；
- 从另一只基金复制策略；
- 将当前策略另存为个人模板；
- 从个人模板创建新计划。

“恢复原始默认策略”是指恢复到该计划最近一次应用内置模板时保存的策略版本，不是直接恢复系统当前的出厂模板。恢复前必须展示差异并生成新的策略版本，原策略及历史事件引用的配置快照继续保留。

配置校验：

- 同一计划的启用档位阈值不得重复；
- 阈值必须大于 0 且小于 100%；
- 补仓倍数必须大于 0，支持小数，V1 默认最多 2 位小数；
- 分期次数必须为 2—12 的整数；
- 间隔周数必须为 1—52 的整数；
- 档位金额不得超过计划设置的单次上限；
- 至少保留一个启用档位；
- 保存前展示按照当前基础金额计算的各档实际金额预览。

示例预览：

```text
基础定投金额：300 元
自定义档位：12%
补仓倍数：1.5 倍
本档计划金额：300 × 1.5 = 450 元
```

### 4.5 策略版本与生效规则

每次保存基金级策略时创建不可变的 `strategy_version`，不得直接覆盖旧版本。

用户修改策略时必须选择：

1. **下一回撤周期生效（默认、推荐）**：当前回撤周期继续使用原策略，新周期使用新版本；
2. **立即生效**：当前周期从下一次检查起使用新版本，但不得补发新策略中已经跨过的浅档位。

立即生效规则：

- 已经成功送达的旧档位不重复提醒；
- 新版本当前最高命中档位如果比所有已送达档位更深，可在下一次检查中触发；
- 删除或停用正在执行的分期档位时，必须提示是否取消未发送的后续期；
- 历史事件永久关联其触发时的策略版本和档位快照；
- 策略修改不得改变历史金额、历史倍数和历史触发原因。

### 4.6 策略模板

内置模板：

- `稳健 / 低波`：3%、5%、8%、12%、18%；
- `核心宽基`：4%、7%、10%、15%、22%；
- `高波宽基`：5%、9%、14%、20%、28%；
- `行业主题`：6%、11%、17%、25%、35%；
- `完全自定义`：用户从零添加档位。

内置模板仅用于初始化，应用模板后产生基金级独立策略版本，不与模板保持自动同步。

个人模板保存：

- 模板名称；
- 回撤档位和倍数；
- 执行方式及分期配置；
- 金额上限规则；
- 创建时间和更新时间；
- 模板 UUID 和版本。

模板只保存策略规则，不保存基金代码、基础定投金额、历史事件或通知状态。

### 4.7 观察标的与购买标的

系统必须把两个对象分开保存：

```text
观察标的（Signal Asset）
- 场内 ETF；
- 用于实时行情、K 线、20 日高点及回撤计算。

购买标的（Purchase Asset）
- 场外 ETF 联接基金；
- 用于生成定投和额外投入提醒。
```

场内 ETF 行情仅是触发信号，场外联接基金最终确认净值以基金公司为准。提醒文案统一使用“按预设规则计算，本次额外投入金额为……”而非确定性的投资建议措辞。

### 4.8 止盈与定投恢复配置

止盈规则按基金独立配置。程序不读取交易账户。初始持仓由用户手工录入，
后续定投和补仓由用户逐笔确认，程序按场外基金官方净值维护当前持仓：

| 字段 | 必填 | 说明 |
|---|---|---|
| 当前实际持有份额 | 是 | 用于计算触发时计划卖出的份额 |
| 当前平均持仓成本 | 是 | 初始值由用户确认；后续按已确认定投、补仓和赎回动态计算 |
| 当前持仓总成本 | 系统生成 | 当前平均持仓成本 × 当前实际持有份额 |
| 持仓最后更新时间 | 系统生成 | 用于展示与审计 |
| 止盈档位 | 是 | 收益率阈值、卖出比例和止盈后的定投金额 |
| 已执行止盈档位 | 系统生成 | 每个档位每轮只允许执行一次 |
| 止盈阶段最高价 | 首次止盈后生成 | 仅用于止盈后恢复定投 |
| 当前定投金额 | 系统生成 | 随止盈和恢复状态变化 |
| 正常定投金额 | 是 | 该基金恢复 100% 定投时的金额 |
| 恢复回撤阈值 | 否 | 用户在基金详情页逐档新增、修改或删除；未配置时不自动恢复 |
| 恢复后定投金额 | 每个恢复档必填 | 与恢复回撤阈值成对配置，不得写死为全局参数 |
| 场外最新官方净值 | 系统抓取、允许人工纠正 | 从天天基金对应场外代码页面获取的最近一期单位净值 |
| 官方净值日期 | 与官方净值同时保存 | 不得晚于当前日期；必须与净值一同保存 |
| 场外官方日涨跌 | 系统抓取 | 与该官方净值同一净值日期的天天基金日涨跌 |
| 盘中估值类型 | 是 | `STANDARD / QDII_HIGH_ERROR`；后者必须显示高误差警告 |
| 持仓口径状态 | 系统生成 | `CONFIRMED / NEEDS_REVIEW`；旧数据迁移后保留原份额和成本，等待用户复核 |

当前平均持仓成本必须与平台可能展示的“摊薄后成本”分开保存。若用户已经发生过
卖出，程序不得擅自把平台显示成本视为真实平均买入成本。

```text
止盈目标价 =
当前平均持仓成本 ×（1 + 止盈收益率）
```

场外联接基金成本与场内 ETF 价格属于不同标的，禁止直接比较。14:50
正式检查仅使用场内 ETF 的盘中涨跌估算场外联接基金当日净值：

```text
场内 ETF 盘中涨跌率 = 14:50 最新价 ÷ 最近一个已完成交易日收盘价 - 1
场外联接基金当日估算净值 = 上一期场外官方净值 ×（1 + 场内 ETF 盘中涨跌率）
场外持仓估算收益率 = 当日估算净值 ÷ 当前平均持仓成本 - 1
```

止盈档位比较必须使用“场外联接基金当日估算净值”与“场外联接基金止盈目标
净值”，不得使用场内 ETF 最新价与场外成本比较。`QDII_HIGH_ERROR` 因交易时段、
汇率、溢折价及跟踪误差等因素只能生成高误差预警。

14:50 达到止盈档位时，事件估值状态为 `ESTIMATED_WARNING`，含义是“盘中估算
可能达到止盈位置”，不是官方净值确认。基金公司公布该交易日官方净值后，用户
在基金详情页录入净值及日期，程序按事件中锁定的目标净值复核为：

- `NAV_CONFIRMED`：官方净值达到目标；
- `NAV_NOT_REACHED`：官方净值未达到目标；
- 未录入时保持 `ESTIMATED_WARNING`。

复核只更新原预警的估值状态，不重复创建止盈卖出事件，不改写原行情、估算值、
目标净值和计划份额快照。用户可在官方净值公布前根据预警自行决定是否赎回；
实际赎回记录与净值复核状态相互独立。

每次自动或人工录入新的官方净值后，该记录成为后续交易日估算使用的“上一期
场外官方净值”。官方净值记录必须按计划和净值日期唯一保存并写入审计日志。

基金详情页必须提供“当前持仓与净值”区域：

1. 用户首次录入或纠正当前实际持有份额和当前平均持仓成本；
2. 页面展示当前持仓总成本、天天基金最新官方净值、净值日期和官方日涨跌；
3. 保存前即时预览该基金全部止盈档位的精确目标价格；
4. 后续每笔定投或补仓只能在用户确认实际执行后进入持仓结算；
5. 成本或份额更正必须展示旧值、新值并写入审计日志；
6. 最终止盈完成后持仓归零；后续确认的新定投重新形成平均持仓成本。

目标价内部计算至少保留 6 位小数；页面和邮件按标的实际价格精度展示，比较触发条件时使用未四舍五入的原始值。页面至少显示：

```text
当前平均持仓成本和持仓总成本
持仓口径状态及最后更新时间
当前实际持有份额
每一档收益率
每一档精确止盈价格
每一档计划卖出比例
每一档是否已经执行
距离下一止盈目标的价格和百分比
```

## 5. 回撤计算规则

### 5.1 基准口径

系统采用短期基准和本轮固定基准两套口径：

- **短期回撤**：相对最近 20 个已完成交易日最高收盘价，用于发现尚未进入周期的短期回撤信号；
- **本轮回撤**：首次触发任一补仓档位时，将当时的 20 日最高收盘价锁定为 `cycle_peak`。本轮后续所有档位、金额和恢复判断均相对固定的 `cycle_peak` 计算。

V1.7 新增第三套独立口径：

- **止盈后回撤**：首次止盈实际执行后，记录并持续更新止盈阶段最高价 `take_profit_peak`，仅用于止盈后降低定投金额的恢复判断。

三种高点必须分开保存：

| 字段 | 中文名称 | 更新方式 | 允许用途 |
|---|---|---|---|
| `rolling_20d_high` | 滚动 20 日最高价 | 随 20 个已完成交易日窗口更新 | 正常状态发现首次回撤补仓信号 |
| `cycle_peak` | 正常补仓周期固定高点 | 正常补仓周期首次触发时锁定 | 同一正常补仓周期的后续档位和恢复 |
| `take_profit_peak` | 止盈阶段最高价 | 首次止盈实际执行后只在创新高时更新 | 止盈后的定投金额恢复 |

禁止使用 `rolling_20d_high` 或 `cycle_peak` 计算止盈后的定投恢复位置，也禁止使用历史 `take_profit_peak` 触发正常状态下的回撤补仓。

14:50 计算时：

- 使用当前交易日前最近 20 个已完成交易日的正式收盘价；
- 同时保存最高收盘价对应的交易日期 `rolling_20d_high_date`；
- 不包含当前交易日；
- 使用行情源提供的前复权收盘价，避免 ETF 分红除息被误判为回撤；
- 停牌日和行情缺失日不计入 20 个有效交易日。

每天只执行一次自动检查，不做当日收盘校准。次一交易日检查时，历史窗口自然纳入前一交易日的正式收盘价。

```text
20 日最高收盘价 = 最近 20 个交易日中最高的正式收盘价
20 日最高日期 = 该最高收盘价对应的交易日期

短期回撤 =
（20 日最高收盘价 - 当前价格）÷ 20 日最高收盘价 × 100%

首次触发时：cycle_peak = 20 日最高收盘价

本轮回撤 =
（cycle_peak - 当前价格）÷ cycle_peak × 100%

首次止盈实际执行后：
take_profit_peak = max(已有 take_profit_peak, 当前价格)

止盈后回撤 =
（take_profit_peak - 当前价格）÷ take_profit_peak × 100%
```

例如：

```text
20 日最高收盘价：1.000 元
本轮固定高点：1.000 元
14:50 最新成交价：0.898 元
短期回撤：10.20%
本轮回撤：10.20%
```

计算精度规则：

- 内部计算至少保留 6 位小数；
- 档位比较使用未四舍五入的原始结果；
- 页面展示保留 2 位小数；
- 触发条件统一为 `drawdown >= threshold`；
- 例如原始回撤 4.996% 即使展示为 5.00%，也不触发 5% 档。

如果 20 日窗口中有多个交易日的最高收盘价完全相同，`rolling_20d_high_date` 取最近一个交易日。行情提供层必须返回“日期 + 收盘价”，不得只返回无日期的价格列表。

### 5.2 为什么不只使用当日涨跌幅

当日下跌 3% 不代表已经达到 5% 累计回撤；当日上涨 1%，也可能仍处于 15% 的深度回撤区间。

因此系统同时展示：

- 当日涨跌幅；
- 当前实时价格；
- 最近 20 日最高收盘价；
- 当前短期回撤；
- 本轮固定高点和本轮回撤（存在活动周期时）；
- 当前所处补仓档位。

尚无活动周期时，短期回撤用于首次触发；活动周期建立后，补仓档位一律以本轮固定高点回撤为准。20 日窗口后续下移不得降低 `cycle_peak`，也不得提前重置本轮档位。

存在活动止盈周期时，止盈后的定投恢复一律使用 `take_profit_peak`。在本轮更高止盈档位尚未执行完之前，即使定投金额已经恢复至 100%，也不得重新启用正常状态的 20 日回撤补仓，避免两套回撤规则同时产生金额建议。

程序必须先按当前阶段选择唯一的回撤基准：

| 当前阶段 | 使用的回撤基准 | 本次可生成的金额决策 |
|---|---|---|
| 正常定投，尚无补仓周期 | `rolling_20d_high` | 首次正常回撤补仓 |
| 正常补仓周期进行中 | `cycle_peak` | 后续正常回撤补仓 |
| 首次止盈已执行 | `take_profit_peak` | 降低或恢复定投金额 |

同一次检查不得同时生成“正常回撤补仓”和“止盈后恢复定投”两类金额建议。界面及通知必须展示当前阶段、采用的高点类型、高点价格和对应回撤率。

用户确认首次止盈实际执行时，如仍存在活动正常补仓周期，该周期转为 `CLOSED_BY_TAKE_PROFIT`：保留原 `cycle_peak`、档位和历史事件用于审计，但停止生成后续正常补仓建议。完成止盈恢复并重新进入正常状态后，不恢复这个旧周期；下一次正常回撤信号重新从当时的 `rolling_20d_high` 建立新周期。

### 5.3 14:50 单次检查口径

14:50 获取的是盘中最新成交数据，不是最终收盘价。程序不强求行情时间精确到 `14:50:00`，而是记录接口实际返回时间。

任务流程：

```text
14:50:00 启动本地任务
14:50:00—14:50:30 获取最新行情
使用接口返回的最新成交价计算回撤
记录行情时间和任务执行时间
当天不再自动复查
```

提醒必须展示：

```text
行情价格：0.898 元
行情时间：2026-07-20 14:50:06
任务执行时间：2026-07-20 14:50:08
本次结果为盘中估算，不代表最终收盘价格。
```

14:50 触发的档位直接作为当天有效触发，不等待收盘确认。如果尾盘价格变化导致最终收盘未达到档位，系统不回滚当天事件；历史记录明确标注数据来源为“14:50 盘中最新价”。

本规则对正常回撤补仓和止盈后恢复定投保持不变。场外联接基金止盈属于例外：
14:50 只形成 `ESTIMATED_WARNING`，后续以基金公司公布的场外官方净值复核为
`NAV_CONFIRMED / NAV_NOT_REACHED`。复核不回滚用户已记录的实际赎回，只提供
审计结果。

### 5.4 手动“立即检查”口径

“立即检查”只刷新最新行情、涨跌、20 日高点、回撤及 K 线等展示数据，不执行策略：

- 不生成固定定投、正常回撤补仓、止盈或恢复事件；
- 不发送桌面通知或邮件；
- 不创建、推进或结束正常回撤周期；
- 不更新止盈后高点、止盈档位状态或当前定投金额；
- 不占用每周补仓次数、当日触发资格或 14:50 正式检查资格。

因此，用户在 14:50 前手动检查后，当日 14:50 正式检查仍须基于届时行情独立计算并正常生成事件及合并邮件。

## 6. 补仓触发机制

### 6.1 逐档触发

档位按照该基金保存的独立策略依次触发；模板档位只在初始化或用户主动应用模板时写入。

同一回撤周期内，同一档位只产生一次“首次触发事件”。是否再次提醒由事件处理状态和重复提醒规则决定。

示例：

1. 周一回撤 4%，不触发；
2. 周二回撤 5.2%，触发 5% 档；
3. 周三回撤 6%，不重复触发 5% 档；
4. 周四回撤 8.3%，触发 8% 档；
5. 周五仍为 8.5%，不重复触发。

### 6.2 快速跨档

如果 ETF 从回撤 4% 直接跌至 10%，系统不应提示用户当天连续执行 5%、8%、10% 三笔补仓。

默认规则：

- 只触发当前最高档位；
- 同一基金同一天只生成一条补仓建议；
- 建议金额受单次上限约束；
- 快速跨过的低档位不再单独补发提醒。

例如基础金额 250 元，直接进入 10% 档：

```text
当前档位：10%
建议金额：250 × 2 = 500 元
```

而不是：

```text
250 + 250 + 500 = 1000 元
```

### 6.3 每周频率限制

本节“每周补仓次数限制”仅适用于额外补仓（回撤补仓），不适用于固定定投。

默认纪律：

- 同一基金一周最多补仓一次；
- 用户可将上限设置为 0、1 或更多次；
- 达到限制后，即使进入新档位，也只提示行情变化，不再建议本周加仓；
- 新一周重新获得补仓资格，但已触发档位不会自动重复触发。

如果本周已经成功发送 5% 档提醒，随后进入 8% 档：

- 创建 8% 档事件并记录为 `SUPPRESSED`；
- 告知用户已进入新档位，但受每周次数限制，本周不建议再次投入；
- 下一周仍处于 8% 或更深档位时，可重新生成一次计划提醒；
- 若下周已经进入更深档位，只处理当前最高档位。

### 6.4 15% 两期补仓计划

首次正式确认进入 15% 档时创建两期计划：

```text
第一期：触发所在周，按 1 倍基础金额提醒。
第二期：下一自然周仍满足回撤 >= 15%，且第一期至少一个通知渠道已成功送达时，再按 1 倍提醒。
```

规则如下：

- 第一周至少一个渠道发送成功后，即视为第一期已经完成提醒；是否实际投入不影响第二期判断；
- 第一周所有启用渠道均发送失败时，第一期保持未送达并按失败策略重试，不生成第二期；
- 第二周回撤恢复至 15% 以下，取消第二期；
- 从 14% 直接进入 20% 时，只处理 20% 当前最高档，不同时创建 15% 计划；
- 15% 两期计划存续期间进入 20% 档，尚未发送的 15% 后续期取消，改按 20% 档处理；
- 每周次数和单次金额上限仍然有效。

### 6.5 回撤周期重置

固定周期锚点规则：

> 首次触发补仓档位时锁定 `cycle_peak`。只有场内 ETF 在两个不同的 A 股交易日的 14:50 自动检查中，最新价均达到 `cycle_peak × 98%` 以上，才视为本轮回撤结束。周五与下一交易日周一属于两个不同的 A 股交易日。

- 只有 14:50 自动检查可以累计恢复检查；手动刷新、失败重试和同一交易日的重复检查均不得累计恢复条件；
- 两次恢复检查之间若本轮回撤重新超过 2%，恢复计数清零；
- 周期未结束前，20 日最高价即使下移也不得替换 `cycle_peak`；
- 周期结束后，下一次短期回撤首次触发时才建立新的 `cycle_peak`。

重置后：

- 5%、8%、10% 等档位恢复为“未触发”；
- 下一轮新的回撤可以再次触发；
- 历史补仓记录保留。

### 6.6 持续补仓上限与人工复核

所有“深度回撤期间按周”策略必须配置有限预算，禁止无限期自动提醒补仓。默认值：

```text
每周补仓：1 倍基础金额
最大执行周数：4 周
单段累计倍数上限：4 倍
单段累计金额上限：可选；填写后与倍数上限共同生效
```

任一上限达到或下一笔将超过上限时：

- 本轮周期保持不变，`cycle_peak` 不重置；
- 计划进入 `PAUSED_FOR_REVIEW`；
- 停止生成新的额外补仓提醒，固定定投不受影响；
- 用户必须在基金卡片点击“确认继续补仓”，才能开启下一段有限预算；
- 人工确认后仍沿用原 `cycle_peak`，重新获得最多 4 周/4 倍的额度；
- 历史事件和已经使用的预算记录保留。

### 6.7 补仓事件与执行状态

每次触发生成独立补仓事件。系统判断依据是“事件是否生成、通知是否成功送达”，而不是用户是否实际投入。

事件状态定义如下：

| 状态 | 含义 | 是否占用正式档位资格 |
|---|---|---|
| `CREATED` | 14:50 已触发，等待发送通知 | 是 |
| `NOTIFIED` | 至少一个启用渠道发送成功 | 是 |
| `DELIVERY_FAILED` | 所有启用渠道均发送失败 | 否，等待重试 |
| `IGNORED` | 用户主动忽略本档 | 是 |
| `POSTPONED` | 延迟到下一交易日提醒 | 是 |
| `SUPPRESSED` | 因周次数限制不重复建议执行；更深档仅发送风险升级通知 | 否 |
| `EXPIRED` | 超过事件有效期 | 是 |

状态转换规则：

- `CREATED → NOTIFIED`：任一启用渠道发送成功；占用本周提醒次数和本轮档位资格；
- `CREATED → DELIVERY_FAILED`：所有渠道发送失败；不占用本周提醒次数，按通知重试策略处理；
- `NOTIFIED → IGNORED`：本回撤周期不再提醒同档，进入更深档仍可提醒；
- `NOTIFIED → POSTPONED`：下一交易日 14:50 检查后提醒一次；如果届时已经脱离该档位，则转为 `EXPIRED`；
- 同一周已经产生补仓建议后，如下一交易日进入更深警戒档，创建 `SUPPRESSED` 风险事件并发送一次风险升级通知；邮件必须明确“本周不重复增加补仓金额”，该事件不允许标记为已执行，也不占用补仓预算；
- 当天不根据最终收盘价回滚或修改事件。

实际投入状态作为独立、可选字段保存：

```text
execution_status：UNKNOWN / EXECUTED / NOT_EXECUTED
executed_amount：用户可选填写的实际金额
executed_at：用户可选填写的执行时间
```

默认值为 `UNKNOWN`。用户只看邮件而不返回确认时，事件仍可正常推进，下一次计算不得因 `execution_status=UNKNOWN` 卡住，也不得假设用户已经买入。

用户操作与两个状态字段的关系必须明确分离：

| 用户操作 | 事件状态变化 | `execution_status` 变化 |
|---|---|---|
| 记录为已执行 | 不变 | `UNKNOWN → EXECUTED` |
| 记录为未执行 | 不变 | `UNKNOWN → NOT_EXECUTED` |
| 忽略本档 | `NOTIFIED → IGNORED` | 不变 |
| 延迟提醒 | `NOTIFIED → POSTPONED` | 不变 |

“是否送达/是否忽略”属于事件状态，“用户是否实际交易”属于执行状态；两者不得互相覆盖或自动推断。

## 7. 定投提醒规则

### 7.1 正常定投

定投开启且当天为设置的定投日时，14:50 生成提醒：

> 今天是 A500 联接基金定投日，计划定投 600 元。  
> 场外代码：022459；观察 ETF：159361。

### 7.2 定投日同时触发补仓

定投金额和补仓金额分开展示：

```text
正常定投：600 元
额外补仓：600 元
今日计划合计：1200 元
```

不能把固定定投误记为补仓。

回撤补仓与固定定投是两条独立资金流：

- 本周已经执行回撤补仓，不得暂停、取消、顺延或减少本周固定定投；
- 同一周先补仓、后到固定定投日时，固定定投照常生成；
- 固定定投日同时触发补仓时，两笔金额分别生成、分别展示并计算合计；
- “同一基金每周最多补仓一次”只限制额外补仓，不限制固定定投；
- 用户确认“已补仓”只更新补仓事件和补仓预算，不得修改当前定投金额或定投任务；
- 只有止盈后的减投规则、用户主动修改定投金额或用户主动关闭定投，才允许改变后续固定定投。

### 7.2.1 定投与补仓的持仓确认

固定定投、回撤补仓及两者同日发生的合并提醒都不得在生成提醒时直接修改持仓。
用户点击“确认已投入”时必须确认：

- 实际扣款金额；
- 申购费用，默认 0，允许修改；
- 净值归属日，默认提醒对应交易日。

结算公式：

```text
净申购金额 = 实际扣款金额 - 申购费用
新增份额 = 净申购金额 ÷ 净值归属日场外官方单位净值
新持仓总成本 = 原持仓总成本 + 实际扣款金额
新实际持有份额 = 原实际持有份额 + 新增份额
新平均持仓成本 = 新持仓总成本 ÷ 新实际持有份额
```

若净值归属日的官方净值尚未公布，确认记录保存为 `PENDING_NAV`，事件执行状态
可以是 `EXECUTED`，但持仓不得提前变化。程序后续同步到相同净值日期时自动结算为
`SETTLED`。同一事件最多存在一笔有效买入确认，重复点击不得重复增加持仓。

天天基金场外净值同步至少保存基金代码、单位净值、净值日期、官方日涨跌、数据
来源和抓取时间。抓取结果日期不等于待结算交易的净值归属日时不得错配。抓取失败
不影响场内 ETF 回撤判断，也不得使用场内 ETF 价格代替场外官方净值结算份额。

止盈目标使用结算后的当前平均持仓成本。新买入结算后，尚未触发的后续止盈目标
随当前平均持仓成本更新；已经创建的历史止盈事件继续保留创建时的成本和目标快照。

### 7.3 定投关闭时

如果定投关闭，但补仓开启：

- 不产生固定定投提醒；
- 补仓金额仍以配置的“基础金额”计算；
- 页面明确说明该金额仅作为补仓计算基数。

这意味着即使关闭定投，仍须保留“每次基础金额”。

### 7.4 金额修改

用户把每次定投从 600 元调整为 800 元后：

- 正常状态下，下一笔尚未生成的固定定投为 800 元；
- 5% 档补仓变为 800 元；
- 10% 档补仓变为 1600 元；
- 修改之前的提醒和历史记录仍保留原金额。

如果修改时正处于止盈后的减投或恢复阶段，保存前必须同时展示：

```text
原 100% 正常定投金额
新 100% 正常定投金额
当前止盈阶段
当前阶段定投金额
各恢复档位对应金额
后续补仓档位对应金额
```

用户必须明确选择：

1. **只修改 100% 正常定投金额和补仓计算基数**：当前止盈阶段金额保持原值；
2. **同时修改当前阶段及恢复档位金额**：用户逐项确认新的阶段金额。

程序不得按比例静默改写止盈后的 200 元、150 元、100 元、50 元等阶段金额。正常金额、当前阶段金额和各恢复档位金额均允许用户维护，但每次修改必须生成新配置版本并保留旧快照。

### 7.5 节假日顺延与周期去重

每次固定定投任务必须绑定定投周期编号，例如 `2026-W30`。

- 周四休市时，默认顺延至下一交易日；
- 连续休市时持续顺延，但同一周期只生成一笔提醒；
- 若顺延日与下一周期正常定投日为同一天，分别展示两期金额，并要求用户确认是否合并执行；
- 用户选择“跳过”时，本周期不再补发；
- 用户修改定投星期后，尚未生成的旧计划任务取消，已经生成的提醒保留历史；
- 场外基金暂停申购时，任务标记为不可执行并停止提醒，恢复申购后不自动补发过期任务。

### 7.6 用户当前止盈与定投恢复规则

本节参数是当前用户确认的个人策略。后续产品实现应支持基金级配置，不得把这些数值写死为所有用户的全局默认值。

本节列出的正常定投金额、止盈后定投金额、恢复回撤阈值及恢复金额都是当前配置示例，用户可以在程序中逐基金修改。恢复档位支持新增、修改和删除，阈值与金额必须成对保存。修改时按照第 7.4 节生成新配置版本，不得改写历史记录。

|---|---:|---:|
| A500 | 159361 | 300 元/周 |
| 恒生科技 | 513010 | 300 元/周 |
| 创新药 | 516080 | 300 元/周 |
| 畜牧养殖 | 516670 | 100 元/周 |

“恢复 100% 定投”指单只基金恢复至上表金额，不要求四只基金在同一时间恢复。

正常定投状态下的额外补仓继续使用第 4.3 节的基金级回撤策略，以及第 5 节定义的 `rolling_20d_high` / `cycle_peak`。这些补仓规则不得与本节的 `take_profit_peak` 恢复规则混用。

#### 7.6.2 卖出份额口径

所有“卖出 30%”均指卖出触发并执行当时实际持有份额的 30%，其中包括：

- 上一档止盈后保留的份额；
- 两个止盈档位之间新增定投获得的份额。

不得按本轮最初份额反复计算，也不得表述为“最终固定剩余 40%”。最终档位卖出执行当时的全部剩余份额。

提醒生成时显示的是按最新手工持仓计算的计划份额。用户实际执行后必须确认或修正真实卖出份额，程序再更新持仓快照、止盈档位和 `take_profit_peak`；仅通知成功不得视为已经卖出。

#### 7.6.3 A500

| 状态 | 卖出动作 | 后续定投金额 |
|---|---|---:|
| 未触发止盈 | 不卖 | 300 元/周 |
| 收益达到 20% | 卖出当时实际持仓的 30% | 200 元/周 |
| 收益达到 40% | 卖出当时全部持仓 | 100 元/周 |

止盈后按 `take_profit_peak` 恢复：

| 当前止盈阶段 | 止盈后回撤 | 定投金额 |
|---|---:|---:|
| 已执行 +20%、尚未执行 +40% | 小于 10% | 保持 200 元/周 |
| 已执行 +40% 并清仓 | 小于 10% | 保持 100 元/周 |
| 任一止盈阶段 | 10% ≤ 回撤 < 20% | 200 元/周 |
| 任一止盈阶段 | 回撤 ≥ 20% | 恢复至 300 元/周 |

A500 回撤达到 20% 后不再自动提高定投金额；如需超过 300 元/周，只能由用户手动修改。恢复档位只改变定投金额，不改变已经执行或尚未执行的止盈档位状态。

#### 7.6.4 恒生科技与创新药

| 状态 | 卖出动作 | 后续定投金额 |
|---|---|---:|
| 未触发止盈 | 不卖 | 300 元/周 |
| 收益达到 20% | 卖出当时实际持仓的 30% | 150 元/周 |
| 收益达到 35% | 再卖出当时实际持仓的 30% | 50 元/周 |
| 收益达到 50% | 卖出当时全部持仓 | 暂停定投 |

止盈后按 `take_profit_peak` 恢复：

| 止盈后回撤 | 定投金额 |
|---:|---:|
| 未达到 10% | 保持当前止盈后金额 |
| 达到 10% | 150 元/周 |
| 达到 20% | 300 元/周 |
| 用户配置的更深回撤阈值 | 用户配置恢复金额；如配置超过 300 元/周，超出部分使用止盈资金 |

#### 7.6.5 畜牧养殖

| 状态 | 卖出动作 | 后续定投金额 |
|---|---|---:|
| 未触发止盈 | 不卖 | 100 元/周 |
| 收益达到 15% | 卖出当时全部持仓 | 暂停定投 |
| 从 `take_profit_peak` 回撤达到用户配置的重新布局阈值 | 不卖 | 恢复至用户配置金额 |

畜牧重新布局阈值及恢复金额均由用户在基金详情页配置。程序不得保留“20%～30%”的模糊条件，也不得替用户选择 20%、25% 或 30%；未配置恢复档位时不自动生成恢复事件。

#### 7.6.6 部分止盈后的回撤与再次上涨

如果已经执行部分止盈，但尚未达到最终清仓档位：

1. 已执行档位不得重复执行；
2. 尚未执行的更高止盈档位继续保留；
3. 定投金额按 `take_profit_peak` 的回撤档位恢复；
4. 后续价格再次达到尚未执行的止盈档位时，继续止盈并按该档位再次降低定投。

例如：

```text
恒科达到 +20%
→ 卖出当时实际持仓 30%
→ 定投降至 150 元/周
→ 从 take_profit_peak 回撤 20%
→ 定投恢复至 300 元/周
→ 后续达到尚未执行的 +35%
→ 再卖出当时实际持仓 30%
→ 定投降至 50 元/周
```

在更高止盈档位尚未执行完之前，本轮止盈周期仍然有效。此时即使定投恢复至 100%，也不得同时启用正常状态的 20 日回撤补仓。

#### 7.6.7 恢复价格

```text
回撤 10% 恢复价 = take_profit_peak × 0.90
回撤 20% 恢复价 = take_profit_peak × 0.80
回撤 30% 恢复价 = take_profit_peak × 0.70
```

止盈阶段价格继续创新高时，程序更新 `take_profit_peak` 并同步更新尚未触发的恢复价。已经触发并生效的恢复档位不得因高点更新而撤销。

#### 7.6.8 止盈周期与下一轮

- 最终止盈档位实际执行后，结束本轮卖出流程；
- 清仓不代表永久退出，定投金额按本节规则保持低额或暂停；
- `take_profit_peak` 继续保留，用于判断定投恢复位置；
- 恢复至 100% 定投后，程序准备下一轮止盈基准成本；
- 新一轮止盈基准成本必须由用户检查当前真实平均买入成本并手工确认后锁定；
- 回到正常状态后不恢复首次止盈前遗留的正常补仓周期，后续正常补仓从新的 20 日回撤信号开始；
- 历史基准成本、目标价、实际卖出和定投金额变化全部保留。

#### 7.6.9 恢复档位配置确认

用户于 2026-07-30 确认：所有基金的恢复回撤阈值和恢复后定投金额全部由前端按基金配置，不设置全局固定值。

1. 基金详情页允许新增、修改和删除恢复档位；
2. 每个已配置档位的回撤阈值和恢复金额必须同时填写；
3. 回撤阈值必须大于 0% 且小于 100%，同一基金不得重复；
4. 恢复金额不得小于 0；0 表示恢复后仍暂停定投；
5. 删除全部恢复档位表示该基金暂不自动恢复定投；
6. 保存后生成新的基金配置版本，历史事件继续引用原配置快照；
7. 旧数据中的空白恢复金额不执行，用户再次保存时必须补全金额或删除该档位。

## 8. 资金池控制（P1）

为了避免多个基金同时触发后，建议金额超出每月预算，P1 增加“补仓资金池”。V1 仅展示各计划理论金额及合计，不自动占用、扣减或分配额度。

### 8.1 配置字段

- 每月投资预算；
- 每月固定定投预计金额；
- 本月补仓池金额；
- 本月已补仓金额；
- 当前剩余额度；
- 是否允许额度结转至下月。

### 8.2 资金不足时

当建议补仓金额超过资金池余额时，显示：

```text
理论建议补仓：1200 元
补仓池剩余：800 元
受资金池限制，本次建议最多补仓：800 元
```

P1 允许用户给计划设置优先级：

1. 核心宽基；
2. 行业增强；
3. 周期交易。

多个基金同时触发时，排序规则为：

1. 用户手动优先级；
2. 回撤档位由高到低；
3. 首次触发时间由早到晚；
4. 计划创建时间由早到晚。

V1 不自动分配额度，仅提醒理论合计可能超过预算；P1 再支持按顺序全额满足或按比例分配。

### 8.3 P1 资金约束优先级

P1 启用补仓资金池后，先按资金池余额确定本次可用金额，再应用持续补仓的 4 周、4 倍及单段金额上限，最终采用更严格的结果。V1 不维护资金池余额，因此本规则不得提前影响 V1 的理论金额计算。

## 9. 提醒内容

每个 A 股交易日 14:50 行情检查结束后，邮件渠道固定发送一封合并汇总邮件。是否存在定投、补仓、止盈或恢复事件，不影响当日汇总邮件发送。

邮件按一次完整检查聚合，不按基金或事件拆分。邮件至少包含：

- 检查日期、实际检查时间和行情口径；
- 成功检查、失败检查、补仓触发、止盈触发和风险升级数量；
- 当日固定定投、额外补仓及计划投入合计；
- 每只 ETF 的最新价格和行情时间；
- 20 日最高收盘价、对应交易日期及相对回撤；
- 本次实际采用的回撤基准类型、价格、日期及回撤；
- 触发的补仓、止盈、减投或恢复动作；
- 止盈基准成本、精确止盈目标价、卖出比例及计划卖出份额；
- 场外上一期官方净值及日期、场内 ETF 昨收和盘中涨跌率、场外当日估算净值；
- 止盈估值状态（盘中估算预警、官方净值已确认或官方净值未达到）；
- `QDII_HIGH_ERROR` 计划的高误差警告；
- 无操作时明确显示“今日未触发定投、补仓或止盈”；
- 盘中估算及用户自行确认提示。

### 9.1 提醒渠道配置

用户可以独立开启桌面通知和邮件：

| 渠道 | 默认状态 | V1 实现方式 |
|---|---|---|
| macOS 桌面通知 | 开启 | 调用 macOS 通知中心；锁屏时是否显示内容服从系统通知设置 |
| 邮件 | 关闭 | 用户配置 SMTP 服务、发件地址和收件地址；启用后每个交易日固定发送一封汇总 |

统一配置项：

- 渠道开关；
- 通知测试按钮；
- 失败重试次数，默认 2 次；
- 单渠道静默时间；
- 是否隐藏锁屏通知中的金额。

桌面通知继续按单个重要事件即时显示；邮件只发送每日合并汇总。邮件未配置或发送失败不得影响桌面通知、行情检查及事件保存。

一次 14:50 检查的通知顺序如下：

1. 完成全部基金计算，并在同一检查批次中保存行情、金额及事件快照；
2. 按该快照逐条发送桌面通知；
3. 桌面通知发送完成后，将同一批次快照聚合成一封邮件；
4. 邮件不得混入该快照保存后才由手动操作、重试或其他任务创建的事件。

```text

```

```text
DAILY_SUMMARY_FAILED

```


规则：

- 每个交易日最多成功发送一封定时汇总邮件；
- 无定投、补仓、止盈或恢复事件时仍然发送；
- 多只基金和多个事件合并到同一封邮件；

- 单只基金失败时，成功基金照常汇总，失败基金进入“检查失败”区域；
- 全部行情失败时仍尝试发送一封运行异常汇总；
- 系统保存发送时间、响应结果和脱敏错误，不得因邮件失败回滚行情和策略事件。

“下一止盈价”指当前锁定基准下最近一个尚未执行的止盈档位目标价。如果尚未锁定止盈基准，或本轮已经没有尚未执行的止盈档位，显示“下一止盈价未设置”，不得猜测或继续显示已执行档位。

## 11. 用户操作状态

提醒生成后，用户可以选择：

- 已补仓；
- 暂不补仓；
- 忽略本次；
- 延迟到下一个交易日提醒；
- 修改本次金额；
- 查看计算过程。

本周次数限制以“至少一个渠道成功送达提醒”为准，而不是以用户确认实际投入为准。用户点击“已补仓”时，系统只记录可选的实际执行信息，不改变此前已经占用的提醒次数。V1 不维护全局资金池余额。

如果用户没有反馈：

- 系统不能默认其已经执行；
- 当天不重复提醒；
- 事件执行状态保持 `UNKNOWN`；
- 不影响下一交易日、新档位或15%第二期提醒的正常计算。

用户操作的具体状态转换以 6.7 节补仓事件状态机为准。

| 用户操作 | 事件状态 | `execution_status` |
|---|---|---|
| 已补仓 | 保持当前已送达状态 | `UNKNOWN → EXECUTED` |
| 暂不补仓 | 保持 `NOTIFIED` | `UNKNOWN → NOT_EXECUTED` |
| 忽略本次 | 转为 `IGNORED` | 保持原值 |
| 延迟到下一交易日提醒 | 转为 `POSTPONED` | 保持原值 |

“修改本次金额”只修改用户实际执行记录或待确认金额，不得回写触发时的理论建议金额和策略快照。

## 12. 非交易日及异常处理

### 12.1 非交易日

周末、法定节假日或休市日：

- 不获取盘中行情；
- 不触发补仓；
- 不发送 14:50 每日汇总邮件；
- 定投提醒按用户设置选择“顺延”或“跳过”。

所有交易判断固定使用 `Asia/Shanghai` 时区和中国大陆交易所交易日历，不使用用户电脑本地时区。交易日历支持临时休市人工配置。

### 12.2 行情获取失败

数据源超时或数据异常时：

- 不使用旧价格生成新的补仓建议；
- 展示最后成功更新时间；
- 标记“行情数据不可用”；
- 自动重试最多 3 次；
- 支持用户手动刷新。

### 12.3 极端数据保护

出现以下情况时停止计算：

- ETF 代码不存在；
- 当前价格为 0；
- 最近 20 日数据不足；
- 价格出现明显异常跳变；
- ETF 停牌；
- 数据时间不是当天；
- 行情源返回非交易状态。

新上市 ETF 不足 20 个交易日时，可使用现有全部交易日，但须明确标注“历史数据不足 20 日”。

## 13. 定时任务幂等与并发

调度器每周一至周五 14:50 尝试启动任务，任务启动后必须按 `Asia/Shanghai` 时区校验当天是否为 A 股交易日。只有校验通过的任务才属于“每个 A 股交易日 14:50”的正式检查；非交易日只记录跳过结果，不生成行情、事件或每日邮件。

14:50 定时任务、人工刷新和失败重试可能同时运行，系统必须保证不会生成重复事件；人工刷新仅写入行情快照，不执行策略。

事件幂等键：

```text
plan_id + trading_date + drawdown_cycle_id + level_id
```

规则：

- 相同幂等键只能成功创建一条事件；
- 重复任务只更新行情检查日志，不重复发送通知；
- 多基金可以并行计算，每个计划内部必须串行更新档位状态；
- 手动刷新不生成策略事件，不修改每周次数、档位状态、恢复计数或每日单次触发状态；
- 所有定时任务记录开始时间、结束时间、执行结果和错误信息。
- macOS 安装版首次启动及版本替换后必须自动安装或校正当前应用路径对应的 `launchd` 任务，不要求用户手动执行命令。
- 桌面端顶部必须显示调度是否启用、最近一次检查时间及成功/失败状态，不得在任务未安装时固定显示“下轮检查 14:50”。

## 14. 默认策略配置

系统首次创建长期定投计划时，默认选择“核心宽基”初始化模板；用户可在保存前选择其他模板或完全自定义：

```text
短期观察窗口：20 个交易日
核心宽基档位：4%、7%、10%、15%、22%
4% 档：1 倍
7% 档：1 倍
10% 档：2 倍
15% 档：首次确认后创建两期计划，每期 1 倍
22% 以上：每周 1 倍，最多 4 周，单段累计最多 4 倍
同一基金每周最多补仓：1 次
单日最多触发：1 次
首次触发后固定：cycle_peak = 触发时 20 日最高收盘价
档位重置：两个不同交易日均恢复至 cycle_peak 的 98% 以上
达到持续补仓上限：PAUSED_FOR_REVIEW，须用户手动确认
```

周期类基金独立模板规划如下，但 V1 不开放：

```text
首次观察仓：1 倍基础金额
相对用户参考成本下跌 5%：再补 1 倍
重新站上 5 日均线并维持 2 日：再补 1 倍
仓位上限：由用户自行填写
不进行无限期自动定投
```

周期策略依赖用户真实成本和趋势条件，放到后续版本；V1 只支持长期定投回撤策略。

## 15. 验收标准

### 15.1 基金配置

- 能添加场内 ETF 代码和场外联接基金代码；
- 能随时修改 100% 正常定投金额；
- 能分别修改当前止盈阶段及各恢复档位的定投金额；
- 能设置星期一至星期五中的任意定投日；
- 能独立关闭定投和补仓；
- 修改金额后，下一次计算立即使用新金额。
- 止盈周期内修改正常金额时，必须让用户选择是否同步修改当前阶段及恢复档位金额；
- 未经用户选择，不得按比例静默覆盖止盈阶段金额；
- 每条追踪计划显示可用的删除按钮；
- 删除前必须二次确认，确认后计划变为 `ARCHIVED` 并退出后续检查；
- 删除计划后历史行情、事件、执行记录和邮件记录仍可查询。

### 15.2 行情计算

- 每个交易日 14:50 自动获取一次行情；
- 能取得当日涨跌幅、实时价格和最近 20 日收盘价；
- 能取得并保存 20 日最高收盘价对应的交易日期；
- 正确计算短期 20 日回撤和固定锚点本轮回撤；
- 首次触发后锁定 `cycle_peak`，20 日窗口下移不得改变本轮回撤基准；
- 非交易日不生成错误提醒；
- 数据失败时不生成基于旧行情的新建议。

### 15.3 补仓计算

假设用户选择含 5%、8%、10% 档位的自定义策略，基础定投金额为 600 元：

- 回撤 4.99%：不补仓；
- 首次达到 5%：建议 600 元；
- 首次达到 8%：建议 600 元；
- 首次达到 10%：建议 1200 元；
- 相同档位第二次检查：不重复建议；
- 基础金额改为 800 元后，10% 档建议 1600 元；
- 本周已补仓时，本周再次触发不得重复建议。
- 本周已经执行回撤补仓后，固定定投日仍正常生成固定定投任务；
- 同日既有固定定投又触发补仓时，两笔金额分别展示且合计正确；
- 每周补仓次数限制不得拦截、取消或减少固定定投；
- 用户确认“已补仓”不得改变当前定投金额；
- 持续补仓达到 4 周或 4 倍上限后进入 `PAUSED_FOR_REVIEW`；
- 未经用户确认不得继续生成额外补仓提醒。

### 15.4 提醒

- 定投日显示固定定投金额；
- 达到补仓档位显示额外补仓金额；
- 达到止盈档位显示止盈基准成本、精确目标价、计划卖出比例和计划卖出份额；
- 同时发生时分项显示并计算合计；
- 每个交易日 14:50 检查结束后只发送一封合并汇总邮件；
- 多只基金和多类事件必须合并，不得按事件分别发送邮件；
- 当日没有定投、补仓、止盈或恢复事件时，仍发送“今日无操作”邮件；
- 无操作邮件显示每只 ETF 的最新价、20 日最高日期、20 日最高价、回撤和下一止盈价；
- 下一止盈价取最近一个尚未执行的止盈档位；止盈基准尚未锁定或本轮无剩余档位时明确显示“下一止盈价未设置”；
- 手动“立即检查”只刷新行情，不生成事件、桌面通知或汇总邮件；
- 桌面通知和邮件必须来自同一检查批次快照，邮件不得混入快照生成后的新事件；
- 单只基金行情失败时，汇总成功基金并单列失败基金；
- 每条提醒展示完整计算依据；
- 明确标注 14:50 数据属于盘中估算并展示实际行情时间。

### 15.5 边界、状态与幂等测试

1. 原始回撤恰好等于 5.000000% 时触发；
2. 展示为 5.00%、原始值为 4.996% 时不触发；
3. 一天从 4% 直接跨到 10%，只生成一条 10% 提醒；
4. 14:50 达到 10% 时生成当天有效事件，之后不因收盘价格变化回滚；
5. 14:50 未达到 10% 时当天不再自动补发，下一交易日重新检查；
6. 本周已成功发送 5% 档提醒后进入 8% 档，事件标记为 `SUPPRESSED`；
7. 8% 档本周因次数限制被 `SUPPRESSED`，下周仍处于该档时允许重新提醒；
8. 用户忽略 8% 档后，同轮进入 10% 档仍可提醒；
9. 定时任务重复执行两次，不得生成两条相同提醒；
10. 行情时间戳不是当天或超过允许时效，不得触发；
11. 修改基础金额后，旧事件金额和配置快照不得变化；
12. 修改档位配置仅影响修改后新生成的事件；
13. 删除或归档计划后，历史记录仍可查看；
14. 新上市 ETF 只有 8 个有效交易日时正确计算并显示提示；
15. 多基金同时触发时，理论合计金额正确；
16. 节假日顺延后，同一定投周期不得重复生成任务；
17. 长期下跌导致 20 日最高价下降时，本轮 `cycle_peak` 保持不变；
18. 手动刷新、失败重试和同一交易日重复检查不得累计恢复条件；
19. 两个不同交易日的 14:50 自动检查均达到 `cycle_peak × 98%` 后结束周期；
20. 持续补仓第 4 次成功送达后进入 `PAUSED_FOR_REVIEW`，第 5 周不得继续提醒；
21. 用户确认继续后仍沿用原 `cycle_peak`，并开启新一段有限预算；
22. 模板仅初始化策略，保存后的基金策略可独立编辑且不被自动覆盖。
23. 14:50 前执行“立即检查”只更新行情展示；随后 14:50 达标时仍正常生成补仓建议和合并邮件。
23. 用户确认已执行后，保留当时行情、金额、档位及渠道发送快照；
24. 15% 第一期所有渠道均发送失败时，不得生成第二期；至少一个渠道送达且下周仍满足15%时可以生成；
25. 15% 计划存续期间进入 20% 档时，尚未发送的 15% 后续期被取消；
26. ETF 除息时使用复权数据，不得因机械价格缺口误触发。

#### 15.5.1 止盈恢复边界测试

1. 止盈后 `take_profit_peak` 创新高时，尚未触发的恢复价同步更新；
2. 已触发并生效的恢复档位不得因 `take_profit_peak` 后续更新而撤销或重算；
3. 部分止盈后恢复至 100% 定投时，尚未执行的更高止盈档位继续保留；
4. 活动止盈周期内不得使用 `rolling_20d_high` 或 `cycle_peak` 触发定投恢复；
5. 正常定投阶段不得使用历史 `take_profit_peak` 触发回撤补仓；
6. 同一次检查不得同时生成正常回撤补仓金额和止盈恢复金额。

### 15.6 止盈、减投与恢复

1. 用户可手工录入实际持有份额和本轮止盈基准成本；
2. 止盈基准成本锁定后，后续定投或部分卖出不得自动移动目标价；
3. A500 基准成本为 1.000 元时，正确计算 1.200 元和 1.400 元目标价；
4. 恒科或创新药基准成本为 1.000 元时，正确计算 1.200 元、1.350 元和 1.500 元目标价；
5. 畜牧基准成本为 1.000 元时，正确计算 1.150 元目标价；
6. “卖出 30%”按执行时最新实际持有份额计算，而不是按本轮初始份额计算；
7. 仅提醒成功而用户尚未确认执行时，不得减少持有份额、降低定投或建立 `take_profit_peak`；
8. 用户确认首次止盈后建立 `take_profit_peak`，后续创新高时只向上更新；
9. 止盈后恢复价分别正确计算为 `take_profit_peak × 0.90 / 0.80 / 0.70`；
10. 活动止盈周期内不得使用 `rolling_20d_high` 或 `cycle_peak` 触发定投恢复；
11. 正常定投阶段不得使用历史 `take_profit_peak` 触发回撤补仓；
12. 同一次检查不得同时生成正常补仓金额和止盈恢复金额；
13. 部分止盈后回撤恢复至 100% 定投时，尚未执行的更高止盈档位仍然保留；
14. 已执行止盈档位在同一轮价格再次穿越时不得重复提醒；
15. 最终止盈确认执行后清空当时持仓，保留 `take_profit_peak` 等待恢复；
16. 首次止盈实际执行时，尚未结束的正常补仓周期转为 `CLOSED_BY_TAKE_PROFIT` 且不再生成补仓建议；
17. 新一轮止盈基准成本未经用户确认不得自动锁定；
18. 用户修改草稿基准时即时重算并预览所有精确止盈目标价；
19. 已锁定基准只能通过二次确认的“更正基准”流程修改；
20. 更正基准后旧值、新值和各目标价变化均写入审计日志。
21. A500 执行 +20% 部分止盈后、回撤不足 10% 时保持 200 元/周；
22. A500 执行 +40% 清仓后、回撤不足 10% 时保持 100 元/周；
23. A500 回撤达到 20% 后恢复至 300 元/周，回撤继续扩大时不得自动提高，除非用户手动修改。
24. 场外止盈成本不得与场内 ETF 价格直接比较；
25. 上一期场外官方净值为 1.000、场内 ETF 昨收为 1.200、14:50 最新价为
    1.224 时，场外当日估算净值应为 1.020；
26. 14:50 估算净值达到目标时只生成 `ESTIMATED_WARNING`；
27. 录入同一交易日官方净值后，原预警准确转为 `NAV_CONFIRMED` 或
    `NAV_NOT_REACHED`，不得重复创建卖出事件；
28. 若 14:50 未触发预警、但后来公布的该日官方净值达到尚未执行的止盈档，
    下一次正式检查必须补建 `NAV_CONFIRMED` 提醒；即使当前盘中已经回落也不得
    丢弃该次历史触达，同一净值日期和止盈档不得重复提醒；
29. 旧锁定基准缺少官方净值口径时标记 `NEEDS_REVIEW`，不得继续按场内价格
    触发场外止盈；
30. QDII 或高误差计划在界面、桌面通知和邮件中均显示“仅作高误差预警”；
31. 官方净值复核状态与用户实际赎回执行状态独立保存，互不覆盖。

## 16. 非功能需求

### 16.1 数据及时性

- 14:50 任务允许延迟不超过 5 分钟；
- 行情时间戳与当前时间相差超过 10 分钟时视为过期数据；
- 单次检查应在 2 分钟内完成，单只 ETF 失败不得阻塞其他计划。

### 16.2 可用性与容错

- 行情获取失败自动重试 3 次；
- 重试间隔采用递增策略；
- 仍失败时记录异常并通知用户，不生成投入建议；
- 单个 ETF 获取失败不得阻塞其他计划计算。

### 16.3 审计记录

每次计算必须保存：

- 使用价格、价格类型及行情时间；
- 20 日历史数据起止日期；
- 回撤基准最高价；
- 当前策略阶段及实际采用的高点类型；
- `rolling_20d_high`、`cycle_peak` 和 `take_profit_peak` 的有效值；
- 原始回撤结果及展示结果；
- 止盈基准成本、目标价、计划卖出份额及用户确认的实际卖出份额；
- 止盈前后定投金额及恢复档位；
- 档位配置快照；
- 基础定投金额快照；
- 每周次数限制快照；
- 14:50 预计档位及实际行情时间；
- 最终事件及用户操作结果。

### 16.4 安全与隐私

- V1 不采集支付宝、银行卡或券商账号密码；
- 不保存可用于真实交易的授权凭证；
- 用户计划及执行记录仅供本人查看；
- 配置修改、删除和事件状态变化必须写入审计日志。

## 18. 最终业务规则摘要

```text
1. 用户自行添加场内 ETF 和场外联接基金。
2. 用户自行设置定投金额、定投星期、补仓档位、止盈档位及相关开关。
3. 每个交易日 14:50 在 Mac 本地获取一次场内 ETF 最新行情。
4. 同时获取最近 20 个交易日正式收盘价。
5. 正常状态首次补仓使用 rolling_20d_high；进入正常补仓周期后使用固定 cycle_peak。
6. 首次止盈实际执行后建立 take_profit_peak，止盈后的定投恢复只使用该高点。
7. 三种高点独立保存，同一次检查只允许一套回撤基准参与金额决策。
8. 补仓金额 = 当前基础定投金额 × 对应档位倍数。
9. 正常补仓同一周期内同一档位只首次触发一次，并受每周次数和有限预算约束；这些限制不得暂停或减少固定定投。
10. 用户手工确认本轮止盈基准成本，锁定后本轮目标价不随定投或部分卖出移动。
10.1 场外止盈目标净值仅与场外估算/官方净值比较；场内 ETF 仅提供盘中相对涨跌信号。
11. 卖出比例按执行时实际持有份额计算，最终档位卖出当时全部剩余份额。
12. 止盈后按基金规则降低定投，并按 take_profit_peak 的 10% / 20% / 30% 回撤档位恢复。
13. 部分止盈后恢复 100% 定投，不取消尚未执行的更高止盈档位。
14. 活动止盈周期内不得同时启用正常 20 日回撤补仓。
15. 仅通知成功不代表用户已交易；持仓、止盈档位和 take_profit_peak 只在用户确认执行后更新。
16. 定投关闭不等于补仓关闭，两者独立控制。
17. 14:50 触发作为当天有效事件，不做收盘校准或回滚。
17.1 场外止盈在 14:50 只生成盘中估算预警；官方净值公布后复核原预警，或为
14:50 后才达到的止盈档补建官方净值确认提醒。
18. 每个交易日正式检查结束后发送一封合并邮件，无操作时也发送；手动“立即检查”只刷新行情，不生成事件或发送通知。
19. 补仓、风险升级、止盈、减投和恢复信息统一合并到当日邮件。
20. 用户可以维护并锁定止盈基准值，程序据此显示并提醒精确止盈位置。
21. 每条追踪计划提供删除按钮；删除采用二次确认和软删除，历史记录保留。
22. 系统只计算和提醒，不自动执行基金交易。
23. 每条历史事件保存行情、高点类型、金额、份额、规则及用户操作快照。
24. 定时任务必须通过幂等键防止重复提醒；人工刷新不得进入提醒生成流程。
25. P1 启用资金池后，先受资金池余额约束，再应用持续补仓上限，取更严格结果；V1 不提前执行该规则。
26. 回撤周期恢复只由两个不同交易日的 14:50 自动检查累计，手动刷新和失败重试不计数。
```

## 19. 成功标准

系统给出的每一笔补仓、止盈、减投或恢复建议，都必须能够清楚回答：

- 依据的是哪个场内 ETF；
- 使用的是哪个价格；
- 当前累计回撤是多少；
- 当前处于正常补仓阶段还是止盈恢复阶段；
- 本次使用的是 `rolling_20d_high`、`cycle_peak` 还是 `take_profit_peak`；
- 触发了哪个补仓档位；
- 基础定投金额是多少；
- 补仓倍数是多少；
- 为什么建议补这个金额；
- 是否受到每周次数限制，以及 P1 启用后是否受到资金池额度限制。
- 本轮止盈基准成本和目标价格是多少；
- 计划卖出比例及按当前持仓计算的计划卖出份额是多少；
- 用户实际执行后，下一档止盈价、当前定投金额和下一恢复价是多少。

## 20. macOS 本地部署方案

### 20.1 产品形态

V1 定位为单用户、个人自用的 macOS 本地工具，不部署公网服务，不要求域名、云服务器或微信小程序。

推荐组成：

```text
本地管理页面（Streamlit）
        ↓
SQLite 本地数据库
        ↓
macOS launchd 每个工作日 14:50 启动 daily_check.py
        ↓
行情适配器批量获取最新价和历史日线
        ↓
计算回撤与止盈位置、生成事件、写入历史
        ↓
macOS 桌面通知 / 每日 SMTP 合并邮件
```

代码结构建议：

```text
app.py                 本地配置和历史查看页面
daily_check.py         14:50 单次检查入口
core/                  回撤、档位和状态机纯业务逻辑
providers/market/      行情数据适配器
providers/notify/      桌面通知和 SMTP 邮件适配器
storage/               SQLite 数据访问和迁移
tests/                 计算、状态、调度和通知测试
```

页面程序与定时任务必须分离。关闭管理页面不能影响 `daily_check.py` 被 `launchd` 调用。

### 20.2 技术选型

| 模块 | V1 方案 |
|---|---|
| 开发语言 | Python 3 |
| 本地页面 | Streamlit |
| 数据库 | SQLite |
| 行情 | 行情适配器接口；首个实现可使用 AKShare，允许后续替换 |
| 调度 | macOS `launchd` |
| 桌面通知 | macOS 通知中心 |
| 邮件 | SMTP，支持 SSL/TLS |
| 日志 | Python logging，按大小或日期轮转 |
| 密钥保存 | macOS Keychain；数据库只保存密钥引用或脱敏值 |

Streamlit 仅承担配置、查询和人工操作界面，不作为后台调度服务。14:50 自动检查由独立的 `daily_check.py` 进程执行，与 Streamlit 是否启动或保持运行无关。

行情模块必须通过统一接口隔离：

```text
get_latest_quotes(symbols)
get_daily_history(symbol, completed_trade_days=20, adjust="qfq")
```

不得把某个免费行情网站的字段和请求逻辑散落在业务计算代码中。行情源失败时可以整体升级或替换而不改补仓规则。

### 20.3 Mac 运行前提

用户的 MacBook 运行条件：

- 保持开盖；
- 长期连接电源；
- 可以锁屏、关闭显示器；
- 系统本身不得进入睡眠；
- 当前用户保持登录；
- 14:50 前后保持网络连接；
- 已授予应用通知权限；
- 若启用邮件，SMTP 配置已经通过“发送测试邮件”。

锁屏不会阻止任务运行，但睡眠、合盖睡眠、关机或断网都会影响任务。应用首页必须展示：

- 上一次成功检查时间；
- 下一次计划检查时间；
- 最近一次失败原因；
- 当前通知渠道健康状态；
- 最近一次行情成功时间。

### 20.4 launchd 调度规则

`launchd` 每周一至周五 14:50 尝试执行，但脚本启动后仍须自行判断 A 股交易日和有效执行时间。

```text
有效执行窗口：交易日 14:45:00—15:00:00
正常计划时间：14:50:00
允许启动延迟：5 分钟
最大运行时间：2 分钟
失败重试：间隔 60 秒，最多 2 次
```

如果 Mac 因睡眠等原因在 15:00 后才补启动：

- 不生成“今天应投入”的补仓提醒；
- 记录 `MISSED_EXECUTION_WINDOW`；
- 发送一条运行异常通知；
- 用户可以手动检查，但结果明确标记为盘后数据，不占用当天 14:50 档位资格。

### 20.5 单次任务执行流程

```text
1. 获取本地进程锁，防止重复运行；
2. 校验 Asia/Shanghai 时间和 A 股交易日；
3. 校验是否处于有效执行窗口；
4. 读取 SQLite 中已启用的计划；
5. 批量获取场内 ETF 最新行情；
6. 获取每只 ETF 最近 20 个已完成交易日的日期及前复权收盘价；
7. 校验行情时间、价格和数据完整性；
8. 计算 20 日最高日期、最高收盘价及当前回撤；
9. 判断补仓档位、止盈档位、回撤周期、每周次数及幂等键；
10. 计算正常定投、额外补仓、止盈份额和止盈后定投金额；
11. 在同一数据库事务中保存计算快照和事件；
12. 按事件发送桌面通知，并按本次检查快照生成一封 SMTP 合并邮件；
13. 分别记录桌面事件和每日汇总邮件的发送结果；
14. 释放进程锁并写入任务完成日志。
```

### 20.6 本地数据与备份

- SQLite 数据库存放于应用数据目录，不放在程序安装目录；
- 支持手动导出计划、事件和执行历史为 CSV；
- 支持一键备份数据库；
- 导入备份前校验数据库版本和完整性；
- 删除计划采用归档方式，历史事件不物理删除；
- SMTP 密码或授权码不得明文导出。

### 20.7 通知渠道验收

macOS 桌面通知：

- Mac 开盖、接电、锁屏但未睡眠时，14:50 可以成功显示通知；
- 用户关闭锁屏内容预览时，不在锁屏界面泄露基金和金额；
- 点击通知可以打开本地详情页。

邮件：

- 配置保存前必须测试连接；
- 发送失败重试 2 次并记录 SMTP 错误；
- 每个交易日检查成功后必须发送一封汇总，零事件也不例外；
- 同一交易日定时汇总成功后，任务重试和手动检查不得重复发送；
- 多基金、多补仓档位和止盈事件必须合并为一封；
- 日志和页面不得显示完整邮箱密码或授权码。

### 20.8 本地版不包含

- 多用户注册和权限系统；
- 云端数据库及多设备同步；
- 公网远程访问；
- 微信小程序；
- 自动控制支付宝、券商或基金交易；
- 电脑睡眠、关机时的云端兜底检查；
- 个人微信客户端自动化。

## 21. 计划导入导出与跨环境迁移

### 21.1 目标

用户能够从 A 环境导出全部业务数据，再导入 B 环境继续使用。迁移后计划配置、历史行情快照、提醒事件、通知记录和可选执行记录保持一致，不要求重新创建计划，也不重复触发已经送达的历史档位。

支持的迁移方向：

```text
macOS → macOS
Windows → Windows
macOS → Windows
Windows → macOS
```

操作系统相关配置不得阻碍业务数据迁移。

### 21.2 导出范围

默认“完整迁移包”包含：

- 基金计划及场内、场外代码映射；
- 定投金额、日期、开关和节假日策略；
- 回撤档位、倍数、每周限制及配置版本；
- 回撤周期和已触发档位状态；
- 历史计算快照；
- 补仓事件及通知送达状态；
- 用户可选记录的实际投入状态和金额；
- 定时任务运行历史和非敏感错误摘要；
- 应用设置、消息模板及通知渠道开关；
- 数据库结构版本和应用版本。

默认不导出：

- SMTP 密码或授权码；
- macOS Keychain 或 Windows Credential Manager 中的内容；
- 日志中的完整第三方响应、个人密码和访问令牌；
- 操作系统绝对路径及本机设备标识。

### 21.3 迁移包格式

导出为单个文件：

```text
etf-assistant-backup_YYYYMMDD_HHMMSS.etfbak
```

`.etfbak` 本质为 ZIP 容器，至少包含：

```text
manifest.json           迁移包元数据、版本、文件清单和校验值
data.sqlite             一致性快照数据库
settings.json           跨平台非敏感设置
templates.json          用户自定义消息模板
checksums.sha256        每个文件的 SHA-256
README.txt              恢复说明和敏感配置提醒
```

`manifest.json` 至少包含：

```json
{
  "format_version": 1,
  "app_version": "1.0.0",
  "schema_version": 1,
  "exported_at": "2026-07-20T14:50:00+08:00",
  "source_os": "macOS",
  "timezone": "Asia/Shanghai",
  "contains_secrets": false
}
```

### 21.4 导出流程

```text
1. 暂停写入并获取数据库备份锁；
2. 使用 SQLite Online Backup API 生成一致性快照；
3. 导出跨平台非敏感配置和消息模板；
4. 生成 manifest 和 SHA-256 校验值；
5. 打包到临时文件；
6. 完整校验迁移包；
7. 原子重命名为最终 .etfbak 文件；
8. 释放锁并记录导出审计事件。
```

导出失败不得留下看似成功但不完整的迁移包。

### 21.5 导入模式

提供两种模式：

1. **整库恢复（推荐）**：B 环境为空或用户希望完全替换时使用；
2. **合并导入**：B 环境已有数据时使用，通过稳定 UUID 合并计划和事件。

整库恢复规则：

- 导入前自动备份 B 环境现有数据库；
- 校验文件类型、格式版本、结构版本和所有 SHA-256；
- 在临时目录完成数据库迁移和完整性检查；
- 全部成功后原子替换正式数据库；
- 任一步失败均回滚，原环境继续可用。

合并导入规则：

- 计划、回撤周期和事件必须使用跨环境稳定 UUID，不依赖本地自增 ID；
- 相同 UUID 的历史事件不得重复插入；
- 相同计划 UUID 但配置不同，默认保留更新时间较新的版本，并在导入前展示差异；
- 用户可选择“保留本机”“采用导入版本”或“复制为新计划”；
- 通知发送记录只合并，不重新发送；
- 已送达档位和周次数状态必须延续，防止迁移后重复提醒；
- 导入期间不运行 14:50 自动任务。

数据库结构版本处理：

- 导入包结构版本低于目标环境时，必须先在临时副本中执行数据库迁移，通过完整性校验后再导入；
- 导入包结构版本高于目标环境时，拒绝导入并提示用户先升级应用；
- 结构迁移或校验失败时不得替换目标环境的正式数据库。

### 21.6 密钥恢复

迁移完成后，对已开启但缺少凭证的渠道标记为 `NEEDS_RECONFIGURATION`：

- 桌面通知只需在新环境重新授权；
- 邮件需要重新录入 SMTP 密码或授权码；
- 用户必须完成“发送测试消息”，渠道才恢复为可用状态；
- 一个渠道待配置不得影响其他渠道和行情检查。

### 21.7 导入导出验收标准

1. A 环境完整导出后，B 环境整库恢复的数据总量、计划 UUID 和事件 UUID 一致；
2. macOS 导出的迁移包能在 Windows 版本导入，反向亦然；
3. 迁移后已触发档位不重复提醒；
4. 迁移后下一次 14:50 检查可基于原回撤周期继续计算；
5. 迁移包篡改任意字节后校验失败且不得导入；
6. 不兼容的未来结构版本必须拒绝导入并给出升级提示；
7. 旧结构版本在临时副本完成数据库迁移后才能替换正式库；
8. 导入中断、磁盘不足或结构迁移失败时，B 环境原数据不受损；
9. 合并导入重复执行两次，不产生重复计划或事件；
10. 迁移包中不存在明文 SMTP 密码、Webhook Token 或其他凭证；
11. 导入成功后，缺少凭证的通知渠道准确标记为待配置；
12. 导出时应用仍可查看数据，但禁止并发修改直至快照完成。

## 22. Windows与macOS双端交付

### 22.1 交付目标

同一套 Python 业务代码支持：

- Windows 10/11 x64 安装包或便携版 EXE；
- macOS DMG，分别支持 Apple Silicon 和 Intel，或提供 Universal 2 构建；
- 两端使用相同数据库结构、迁移包格式和业务规则；
- 用户不需要预装 Python 或手动安装依赖。

### 22.2 平台抽象

平台相关能力必须通过接口隔离：

```text
SchedulerProvider
├── MacOSLaunchdProvider
└── WindowsTaskSchedulerProvider

DesktopNotificationProvider
├── MacOSNotificationProvider
└── WindowsToastProvider

CredentialStore
├── MacOSKeychainStore
└── WindowsCredentialManagerStore
```

行情、回撤、档位、迁移、消息模板和 SQLite 逻辑不得包含平台判断。

### 22.3 打包策略

- 使用 PyInstaller 或经过验证的同类工具分别在对应操作系统原生构建；
- 不从 Windows 交叉生成 DMG，也不从 macOS 直接生成 Windows EXE；
- GitHub Actions 使用 Windows 和 macOS 构建矩阵；
- 每个发布物生成 SHA-256 校验文件；
- macOS 正式分发需规划代码签名和公证；未签名测试包必须明确提示 Gatekeeper 限制；
- Windows 正式分发需规划代码签名；未签名测试包必须说明 SmartScreen 提示；
- 打包后首次启动自动创建应用数据目录和数据库，不覆盖已有数据。

### 22.4 部署指南

仓库必须提供：

```text
README.md                         项目介绍和快速开始
docs/macos-installation.md        macOS 安装、权限、开盖接电与防睡眠设置
docs/windows-installation.md      Windows 安装、任务计划和通知权限
docs/notification-setup.md        桌面通知和 SMTP 邮件配置
docs/backup-and-migration.md      导出、导入、合并、回滚和密钥重配
docs/troubleshooting.md           行情、定时任务、通知和数据库排障
docs/development.md               本地开发、测试和打包命令
SECURITY.md                       凭证处理和漏洞报告方式
```

所有指南必须在干净环境中走查，不得只记录开发机器上的隐含步骤。

### 22.5 测试与发布门槛

上传 GitHub 和创建 Release 前必须完成：

- 回撤计算和档位状态机单元测试；
- 提醒送达闭环和消息模板快照测试；
- SQLite 结构迁移测试；
- 完整恢复、合并导入、重复导入和损坏包测试；
- macOS ↔ Windows 跨平台迁移测试；
- 行情失败、断网、过期行情和任务重复启动测试；
- SMTP 适配器的模拟测试，不在 CI 使用真实密钥；
- EXE 和 DMG 的全新安装、升级、卸载及数据保留测试；
- macOS 锁屏未睡眠条件下的 14:50 任务测试；
- Windows 锁屏条件下的任务测试；
- 文档安装步骤走查；
- 所有自动化测试通过且无高危依赖漏洞。

### 22.6 GitHub交付

最终仓库至少包含：

- 完整源代码；
- 数据库迁移脚本；
- 自动化测试；
- 示例配置但不包含真实密钥；
- `.gitignore` 排除数据库、日志、迁移包和凭证；
- GitHub Actions 测试及双平台构建工作流；

- 部署、迁移和排障文档；

任何真实邮箱密码、Webhook、访问令牌、个人基金数据和本地数据库都不得提交到 GitHub。最终推送和创建 Release 前，应由用户确认目标仓库、可见性和发布版本号。
